# Future Improvements / Known Technical Debt

This document tracks considerations raised during development that were deliberately deferred — these aren't bugs, they're conscious scope decisions worth revisiting later.

---

## Performance

- **`WorldItemHoverDetector` raycasts every frame**, regardless of whether the mouse actually moved. Irrelevant with few items on screen; if an area ends up with many simultaneous drops, consider only re-raycasting when the pointer position actually changes.
- **`EnemyController.DetectPlayer()`** runs `Physics.OverlapSphere` every `Update()` while the mob is Idle. Fine with few mobs; with dozens on screen, an interval (e.g. every 0.2–0.5s) would be cheaper than every frame.
- **Domain Reload not optimized** — `Edit > Project Settings > Editor > Enter Play Mode Settings` allows disabling "Reload Domain" to drastically speed up entering Play Mode. Deferred because it requires extra care with static state/singletons (state can "leak" between test sessions).

## Architecture / Organization

- **`Prefabs/Characters` is still empty** — the Player still exists only as a scene object, never turned into a real prefab, unlike `Prefabs/Enemies` (Poring/Poporing are now proper Prefab Variants). Worth doing before the Player gets iterated on further, since scene-only changes are harder to review in Git diffs than prefab changes.
- **Player GameObject reorganization into child GameObjects, documented and audited, execution pending (manual Editor work).** The single Player object had grown to ~33 components in one flat Inspector list. A full audit (every script's `[RequireComponent]`/`GetComponent<T>()`/`[SerializeField]` usage) found the codebase already decoupled enough — almost everything is wired by dragging serialized references rather than same-object `GetComponent` calls — that splitting into child GameObjects needs no code changes at all, only three groups have to stay together (`CharacterStatsHolder`+`HealthComponent`+`ManaComponent`+`PlayerDeathHandler`; `PlayerSkillCaster`+`SkillTargetingController`; and `NavMeshAgent`+`CharacterMovementController`+`PersistentPlayerAnchor`+`PlayerCombatController`, the last group because those are what physically move/rotate the player and what the camera follows). The real cost turned out to be elsewhere: Unity has no native "move component to another GameObject" — the only path is Copy Component → Paste Component As New → Remove Component, which creates a new instance and breaks every existing reference pointing at the old one, including from UI scripts outside the Player hierarchy (`PlayerHudUI`, `HealthBarUI`, `InventoryUI`, `SkillBookWindowUI`, `SkillHotbarSlotUI`, and others). The full target layout, the step-by-step Editor procedure, and the complete post-move rewiring checklist (every affected field, old vs. new location) are written up in `Documents/PLAYER_HIERARCHY_REORGANIZATION.md` — this is manual Editor work by nature (too much serialized cross-reference surface to hand-edit the scene YAML safely), not something to attempt blind.
- **`HealthBarUI` and `ManaBarUI` are near-identical duplicates** (same Slider-driving logic, different source component). A unification via a shared `IResourceProvider` interface was implemented and then deliberately reverted back to two separate scripts, by team preference (simplicity/independence over DRY in this case). Worth remembering before re-proposing the same unification later.
- **`Project.DebugTools` is not restricted to the Editor platform** (unlike `Project.EditorTools`). Debug loggers (`HealthDebugLogger`, `EquipmentDebugLogger`) could end up in the final build if the components are forgotten on scene objects before publishing.
- **No automated tests** cover the pure logic classes (`Inventory.TryAddItem`, `EquipmentManager` multi-slot/eviction) — good candidates for the Unity Test Framework, since they've caused subtle bugs more than once during manual development.

## Balancing (placeholders assumed deliberately)

- **Fixed: real stat point cost curve implemented.** New `RagnarokStatPointCostStrategy` (`Project.Character.Stats`) replaces the flat 1-point placeholder, applying the documented iRO Wiki formula (`floor((X-1)/10) + 2` for stat value X = 1–99) so raising a stat costs progressively more as it climbs, in bands of 10 (2 points from 1–10, 3 from 11–20, ... 11 from 91–99). `PlayerStatsController.Awake()` now constructs `CharacterBaseStats` with this strategy instead of `FlatStatPointCostStrategy`. Scoped to the 1–99 range only, matching `CharacterBaseStats`'s current `MaxStatValue`; the steeper 100–129 tier (third class only, `4 × floor((X-100)/5) + 16`) is out of scope until stats above 99 are supported. `FlatStatPointCostStrategy` itself was left in the codebase (unused by any scene/component now) as a simple reference `IStatPointCostStrategy` implementation — useful for unit tests wanting a predictable, non-scaling cost — with its doc comment updated to say so; delete it manually if it's judged not worth keeping around as dead code.
- **Fixed: real stat points-per-level-up curve implemented.** New `RagnarokStatPointsPerLevelStrategy` (`Project.Character.Stats`, alongside a new `IStatPointsPerLevelStrategy` interface mirroring `IStatPointCostStrategy`'s separation of "how much" from "when") replaces the flat 5-points placeholder (`PlayerExperience.statPointsPerLevel`, now removed), applying the documented iRO Wiki tiers: `floor(X/5) + 3` under level 100, `floor(X/10) + 13` from 100–150, `floor((X-150)/7) + 28` from 151–200 (X = the level before the level-up). `PlayerExperience.AddExperience` now captures the level *before* incrementing it (`levelBeforeThisLevelUp`) and passes that into the strategy — the previous flat version didn't need this distinction, but the tiered formula does, since `GrantPoints` was already being called after `BaseLevel++`. Applied beyond level 200 by continuing the 151–200 tier's formula rather than throwing, since `PlayerExperience` has no level cap today. **Known source-data discrepancy, not fixed since it's in the reference data, not the code**: the Design Data Tracker's own lookup table lists 27 points for level 150, while its own formula re-evaluated at exactly level 150 gives 28 — a one-level inconsistency between the tracker's formula and its lookup table at the single boundary between the two tiers. The formula is used as documented, in `RagnarokStatPointsPerLevelStrategy`'s own XML remarks.
- **`LinearExperienceCurve`** (XP required per level): still a fully open placeholder (100 × current level). The iRO Wiki Stats reference documents stat-point *rewards* per level, not XP *thresholds* — that curve needs a different source (e.g. the wiki's Experience/Levels pages) when it's tackled.

## Incomplete systems / hooks for future features

- **Quasi-stats not yet modeled**: Attack Range (partially covered by existing attack/aggro ranges), Cast Time and Cast Delay (skills cast instantly today, no channeling — `Cooldown` itself is now implemented per-skill in `PlayerSkillCaster`), Critical Hit Shield, Perfect Dodge, Perfect Hit, and Status Effect Resistance (no status effect system exists). See the Design Data Tracker's "Quasi-Stats" sheet for the full reference.
- **Movement Speed is correctly NOT tied to AGI** — this matches Ragnarok Online's actual behavior (a common misconception is that it should be). Worth remembering before ever "fixing" this as if it were a bug.
- **Stat Points Reset** — no mechanism exists to respec invested stat points. Ragnarok Online offers this via NPCs/consumables/one-time resets; a simplified version (without the advanced-class trappings) is a plausible near-future QoL addition.
- **Talent Stats (POW/STA/WIS/SPL/CON/CRT) and Level 200+ substats (P.ATK/S.MATK/RES/MRES)** — explicitly out of scope for now. These assume fourth-job classes and very high character levels, far beyond the current roadmap; documented in the GDD (Section 3.7) purely for future reference, not as near-term work.
- **Grid-based (SQM) movement, considered and deferred.** Explored making click-to-move snap to a Ragnarok-style square grid (`GridSystem`/`GridVisualizer`, later reverted). Worth revisiting once the project needs it more concretely — likely alongside the authoritative-server migration, since grid coordinates are cheap to sync/validate compared to free-form `Vector3` positions. Key open decisions for whenever this comes back:
  - Whether WASD movement should also be grid-locked, or stay free while only click-to-move/pathing snaps to cells (asymmetry vs. consistency trade-off).
  - Cell size, chosen carefully since it will affect every range/distance value in the game (attack range, aggro radius, skill AoE) once adopted — expensive to change later.
  - Character footprint in cells (1x1 vs. larger, e.g. 3x3) — not yet decided.
  - Whether the visual grid indicator needs to be visible in-game (shader/mesh) or Scene-view-only (Gizmos) is enough.
- **"Ammo" item type is now implemented** — see the new "Class differentiation" section below for details. (Previously noted here as not implemented; kept as a pointer since this note was referenced from a few other places.)
- **Fixed: `ItemDefinition` now has an `OnValidate()`** guarding against inconsistent Inspector configuration. It runs only when `ItemType` is `Equipment` and logs a `Debug.LogWarning` (pointing at the asset, not thrown as an error, so it doesn't block editing) for two cases: `Is Stackable` left checked on equipment, and no `Required Slots` assigned at all — the latter is not just cosmetic, since `EquipmentManager.MakeRoomFor`/`ResolveTargetSlots` would silently let such an item "equip" without ever occupying a slot.

## Player animations (structure scaffolded, manual steps pending)

- **Animator structure added, clips not yet plugged in.** New `PlayerAnimatorController` (`Assets/Scripts/Character/Animation`, own `Project.Character.Animation` asmdef) exposes `SetMovementSpeed`, `TriggerAttack`, `TriggerCast`, `SetIsDead` and is wired into `CharacterMovementController` (Idle/Run), `PlayerCombatController` (Attack), `PlayerSkillCaster` (Cast) and `PlayerDeathHandler` (Death) via `?.` calls, so nothing breaks if the field is ever left unassigned. New `Assets/Animations/Player/Player.controller` has five states (Idle, Run, Attack, Cast, Death), a `Speed` float, `Attack`/`Cast` triggers, an `IsDead` bool, and the transitions between them — but every state's Motion slot is still empty (`m_Motion: {fileID: 0}`), since no actual clips exist yet.
- **Death is a held state, not a one-shot trigger.** `PlayerDeathHandler.HandleDeath()` sets `IsDead = true` (Any State → Death, won't re-trigger while already dead) and the respawn routine sets it back to `false` once the countdown ends and the player is warped/healed (Death → Idle). This intentionally holds the death pose for the whole respawn countdown instead of auto-returning to Idle like Attack/Cast do.
- **Remaining steps are Editor-only, not scriptable**: for each Mixamo FBX, set Rig → Animation Type → Humanoid, Configure → Apply; then extract/rename the individual `.anim` clips under Animations tab; then drag each resulting clip into the matching state's Motion field in the Animator window (Idle, Run, Attack, Cast, Death); then drag the FBX's generated Avatar into the Player GameObject's `Animator` component (currently `m_Avatar: {fileID: 0}`). Sanity-check the graph visually in the Animator window afterward — this asset type was hand-authored as YAML rather than built in-Editor, so transitions/parameters are unverified by an actual Play Mode run.
- **`Male/Base.fbx` and `Female/Base.fbx` have no skeleton at all** (confirmed by binary inspection: zero `LimbNode`/`Deformer`/`Cluster`/`Skin` markers in either file, versus dozens of `LimbNode` entries in the Mixamo-sourced animation FBX like `Running.fbx`). Both are static meshes — no Humanoid mapping is possible until they're rigged. Fix: run each through Mixamo's auto-rigger (Upload Character → mark reference points → download with Skin), which produces a `mixamorig:`-skeleton FBX that replaces the current `Base.fbx`; only then can Rig → Humanoid → Configure/Apply succeed. Once each has its own Avatar, the same animation clips (kept once in the shared `Assets/Models/Player/Animations/` folder, not duplicated per gender) drive both, since Humanoid retargeting works in muscle space rather than against a specific skeleton.
- **Ranged (bow) attack animation added: `AttackRanged` state and trigger.** `Player.controller` gained a fifth combat state, `AttackRanged` (Any State → `AttackRanged` on the new `AttackRanged` trigger, exit-time transition back to Idle — mirrors the existing melee `Attack` state exactly), and `PlayerAnimatorController` gained `TriggerRangedAttack()` alongside the existing `TriggerAttack()`. `PlayerCombatController.PerformAttack()` picks between them based on `EquipmentManager.IsMainHandWeaponRanged()` — the same weapon-driven check already used for the Archer's ammo consumption — rather than checking the player's class directly, so any future ranged weapon on any class plays the bow animation automatically. Like the original five states, `AttackRanged`'s Motion slot is left empty (`m_Motion: {fileID: 0}`): it needs the same manual Editor steps documented above (Mixamo rig, extract clip, drag into the state) before it actually plays anything.
- **Attack damage timing went through two iterations before landing on the current design: damage now applies immediately when an attack fires, in step with the animation trigger, the same way skill casts already worked.** The first iteration deferred damage until the clip's real length had elapsed (`PlayerAnimatorController.GetActiveStateLength()`, reading `Animator.GetCurrentAnimatorStateInfo(0).length`/`GetNextAnimatorStateInfo(0)`), intended to make a hit land when the swing visually connects rather than the instant it starts. In practice this interacted badly with the Animator exit-time bug below: every auto-attack tick queued a fresh wait-for-animation coroutine, and when a cut-short/restarted attack state made that wait read inconsistently, the player would visibly restart the swing animation several times before a hit ever landed — reported as "the attack animation plays repeatedly without actually attacking." Reverted in favor of a direct hit: `PlayerCombatController.PerformAttack()` now triggers the Attack/AttackRanged animation and calls `DealHit()` in the same call, no coroutine, no delay, no fallback constants (`meleeAttackHitDelaySeconds`/`rangedAttackHitDelaySeconds` were removed along with `GetActiveStateLength()`, which is now unused). The tradeoff is explicit: a hit is guaranteed to register the moment the attack fires, at the cost of not waiting for the swing/arrow-release frame — acceptable for this prototype's pacing, and something a proper Animation Event could revisit later if visual sync becomes a priority.
- **Fixed: the Attack and AttackRanged animations were being cut short almost as soon as they started, restarting on the next auto-attack tick instead of ever playing through.** Root cause: their exit transitions back to Idle (`Player.controller`, states 100024 and 100029) had `m_ExitTime: 0.9` set but `m_HasExitTime: 0` — in Unity, a transition with exit time disabled and no conditions is treated as always satisfied and fires on the very next evaluation, so the state was abandoned almost immediately regardless of the `m_ExitTime` value sitting unused right next to it. `AttackRanged`'s copy of this bug was introduced by mirroring `Attack`'s existing (already broken) transition when the ranged state was added; `Attack` itself had carried it since the original five-state controller, before this session. The working `Cast` state's exit transition (100025) already had `m_HasExitTime: 1` and was the reference used to fix both. Both now correctly hold their state until 90% through the clip before blending to Idle — this fix stands independently of the damage-timing reversal above; the animation itself still needs to play through properly even though damage no longer waits for it.
- **Fixed: basic-attack and skill range checks used full 3D distance, which a target's vertical animation (a hop, a jump arc) could push across the range threshold on its own** — reported as the player repeatedly re-triggering the ranged attack animation and Snipe seemingly needing several attempts before landing, traced to Poring's hop moving its collider's world Y position enough to flicker a borderline distance in and out of range every bounce, compounding with the Animator bug above (a cut-short attack retriggering as soon as range read true again). Fixed with a new `CombatRangeMath.HorizontalDistance()` (`Project.Character.Combat`), which zeroes the Y component before measuring — used by `PlayerCombatController.Update()`'s attack-range check and both range checks in `PlayerSkillCaster` (`HasValidDamageTarget`, `TryCastDamage`). Vertical position no longer affects whether a target is in reach; only horizontal movement does.

## Skill system UI (implemented)

The Skill Book and Skill Hotbar windows are implemented: drag-and-drop from a learned skill's icon in the Skill Book onto any of the 10 hotbar slots (`PlayerSkillHotbar`, keys 1-9 and 0) binds it to that slot, and each hotbar slot (`SkillHotbarSlotUI`) reflects real-time availability via `PlayerSkillCaster.GetAvailability` — normal icon when ready, grayscale with a countdown timer (`GetCooldownRemaining`, shown to 1 decimal place) while on cooldown, red tint when blocked for any other reason (not learned, insufficient mana, no valid target). The Skill Book (`SkillBookWindowUI`/`SkillBookEntryUI`) lists every skill available to the current class with icon, name, current/max level, mana cost, and cooldown, plus a Learn button spending a `PlayerJobProgress` skill point. Both the Skill Book rows and the hotbar slots also show the shared `SkillTooltipUI` on hover (icon, name, description, mana cost, cooldown) — the same shared-instance pattern `ItemTooltipUI` already uses elsewhere.

Known gaps left from this pass:

- **No minimum-level requirement to learn a skill**, only class restriction. `SkillDefinition` doesn't have a `requiredLevel` field yet; the quasi-stat gap for this was already noted below.
- **Hotbar slot assignments are now persisted** as part of the save system — see the new section below. Window position/layout is now persisted too (see "UI Window System" further down).
- **`PlayerSkillHotbar.SlotCount`** was bumped from 4 to 10 (keys 1-9 and 0) after the initial 4-slot version shipped. Because `slots` is a `[SerializeField]` array sized from that constant only at authoring time, existing scene/prefab instances kept their old serialized array length (4) even after the constant changed — `GetSkill`/`SetSkill` then threw `IndexOutOfRangeException` for the new slot indices until the array was manually resized to 10 in the Inspector. Worth remembering for any future constant-driven array resize: bumping the constant in code does not resize already-serialized data: check the Inspector every time.

## Skill targeting (implemented)

A Damage skill (e.g. Snipe, Bash) can now be cast without an enemy already selected, instead of just failing. Pressing its hotbar key (or clicking its hotbar slot) with no valid target opens a target-picking mode; the previous behavior (skill fires immediately against whatever's already targeted, if in range) is unchanged when a valid target already exists.

- **Flow**: `PlayerSkillCaster.TryCastSkill` checks `HasValidDamageTarget(skill)` (now public, since `SkillTargetingController` re-checks it after a pick) before the normal Heal/Damage dispatch; if the skill is a Damage skill with no valid target, it hands off to `SkillTargetingController.Instance.BeginPicking(skill)` and returns false instead of failing outright. `SkillHotbarSlotUI.OnPointerClick` was widened to let `SkillAvailability.NoValidTarget` through the click (previously only `Ready`), so clicking a hotbar slot with nothing targeted starts picking rather than doing nothing.
- **While picking** (`SkillTargetingController`, new, `Project.Character.Combat`): every frame, Escape cancels; hovering the mouse over an enemy (a raycast against `enemyLayer`, skipped while the pointer is over UI, filtering out dead `IDamageable`s) shows the white targeting ring at that enemy; right-clicking a hovered enemy confirms. Pressing a different skill's hotbar key while already picking calls `BeginPicking` again, which simply replaces `pendingSkill` and clears the current hover — no explicit "switch" handling needed. Confirming calls `PlayerTargetSelector.SelectTarget()` (the same call normal left-click targeting already uses), so the player enters ordinary combat mode with that enemy — auto-attack and every other skill work on it from then on, not just the one that started the pick — and then re-attempts the original skill if it's now in range.
- **Visual indicators** (`CombatTargetIndicatorsUI`, new, `Project.UI`, sits alongside `SkillTargetingController` on the Player): a white ring (`SkillTargetPickerRing`) follows whatever enemy is currently hovered during picking; a red ring (`CurrentTargetRing`, reusing the existing red `WarpIndicator.mat` rather than a new material) follows the player's actual combat target and updates on `PlayerTargetSelector.TargetChanged` — so it moves or disappears immediately on walking to a new target, switching target, or losing the target, matching a normal MMO's "you are fighting this" indicator. Both rings are flat discs (`GroundRingFollower`, a new position-only follow component — deliberately simpler than `WorldSpaceHealthBarFollower`, since a ground ring shouldn't billboard to face the camera) built from the same "squashed built-in Cylinder + unshadowed MeshRenderer" pattern already used for `WarpDisc`, hand-authored directly in `Prototype_Map01.unity` alongside the existing manually-added objects there (fileID block `900000070` onward — the scene's own convention for hand-added objects, distinct from Unity's normal large random fileIDs).
- **Assembly changes**: `Project.Character.Combat` (`SkillTargetingController`'s `IsPointerOverUI` check) now references `UnityEngine.UI` for `UnityEngine.EventSystems.EventSystem`; `Project.UI` (`CombatTargetIndicatorsUI`'s `PlayerTargetSelector` field) now references `Project.Character.Movement`; `Project.World` (`MapBootstrap` re-wiring the new controller's camera per map, same pattern as the click/hover cameras) now references `Project.Character.Combat`. All three were checked against the full dependency graph before adding — `Project.UI` already depended on `Project.Character.Combat`, so `Character.Combat` could not reference back into `Project.UI` without a cycle; `SkillTargetingController` was designed with zero UI knowledge for exactly this reason, exposing only a `HoveredEnemyChanged` event that `CombatTargetIndicatorsUI` subscribes to from the UI side.
- **Not yet implemented**: a target pick only works via the mouse (raycast + right-click) — no controller/keyboard-only path exists. Ally-target skills still don't have a picking flow of their own (see the existing "Ally-target skills" gap further below) — `BeginPicking` is only ever invoked for Damage skills today. Range checks in this flow (`PlayerSkillCaster.HasValidDamageTarget`) already use the horizontal-only distance fix noted above, so a target's hop/jump animation doesn't flicker it in and out of skill range right after picking.

## Planned skill system expansion (documented, not implemented)

The current skill system (`SkillDefinition`, `PlayerSkillCaster`) only supports instant single-target Damage or Heal effects. Three kinds of skills are planned but deliberately not built yet — noted here with enough shape to avoid re-deriving the architecture later:

- **Temporary buffs and debuffs** (e.g. +20% ATK for 30s, -10% DEF for 15s). Needs a new `StatusEffectDefinition` (which stat, magnitude, duration) and a per-character `StatusEffectController` tracking active effects and their remaining time, applying/removing modifiers. This becomes a third layer in the stat pipeline, alongside the existing Base Stats + Equipment layers (`IStatProvider`/`EquippedStatsView`) — likely another `IStatProvider` implementation that sums active effect modifiers.
- **Ground-targeted area skills with no fixed target** (e.g. a Fire Wall that damages whoever walks into it, an AoE heal zone). Needs a different cast flow from today's (which always resolves to a specific `IDamageable`): the player would click a world position instead of selecting a target, spawning a persistent "zone" object (trigger collider + duration timer) that applies its effect to anything that enters/stays inside it, checking layers to determine who it affects (enemies only, allies only, or both, depending on the skill).
- **Elemental damage and resistances** (Fire, Ice, Holy, Dark, Wind, Electric, Neutral, etc.). Needs an `Element` enum, an optional `Element` field on `SkillDefinition` (and eventually weapons), and a per-element resistance/weakness table added to `CharacterStatsDefinition` (or a new asset type for enemies specifically) — damage would multiply by the target's resistance value for the attack's element. Connects to the already-noted Status Effect Resistance quasi-stat gap.

- **Ally-target skills (`SkillTargetType.Ally`) currently behave identically to Self-target** — `StrongHeal` can only heal the caster today, since no "select another player as a target" mechanic exists yet (there's no multiplayer to test it against). The data field is in place; only the targeting input is missing.

None of this is scheduled — it's here so a future skill-system pass starts from an already-thought-through shape instead of a blank page.

## Player feedback (UX) (partially implemented)

The two silent-failure cases previously noted here now report why through a new generic feedback channel:

- **`PlayerFeedbackChannel`** (new, `Project.Combat`) is a static event (`Action<string> MessagePublished`, raised via `Publish(string)`) rather than an Instance-based hub like `ItemTooltipUI`/`SkillTooltipUI` — deliberately, since the two publishers (`EquipmentManager` in `Project.Items`, `ItemPickup` also in `Project.Items`) live in gameplay assemblies that must not depend on `Project.UI` (the dependency graph only runs the other way — see the "Skill targeting" section above for the same constraint). `Project.Combat` was chosen as the channel's home because it's already a shared leaf assembly (only references `Project.Character.Stats`) that both `Project.Items` and `Project.UI` already reference, so wiring this up needed zero `.asmdef` changes.
- **`EquipmentManager.MeetsRequirements`** now calls `PlayerFeedbackChannel.Publish(...)` with a specific message before returning false — "Level X required to equip {item}" or "Your class cannot equip {item}", depending on which check failed.
- **`ItemPickup.TryCollect`** now publishes "Maximum weight reached: couldn't pick up {item}" when `Inventory.TryAddItem` fails. `Inventory` itself was deliberately left untouched — it's a plain, unit-testable C# class by design (see its own doc comment), and publishing a UI-facing message from inside it would compromise that.
- **`PlayerFeedbackUI`** (new, `Project.UI`) subscribes to `MessagePublished`, shows the message in a fixed screen location, and hides it again after `displaySeconds` (default 2.5s). A new message replaces whatever's currently shown and restarts the timer rather than queuing — adequate for a prototype where these fire rarely and never overlap in practice.
- **Message language note**: these three messages are in English, unlike `ItemTooltipUI.BuildRequirementsText`'s hardcoded Portuguese labels ("Nível requerido", "Classes", "Qualquer classe"). The UI text language isn't consistent across the project yet — worth a deliberate pass (and probably a proper localization approach, rather than hardcoded strings either way) once the UI text surface grows further.
- **Not yet wired into the scene.** Unlike the skill-targeting rings (simple Transform + MeshRenderer objects, safe to hand-author directly in the scene YAML), a proper UI toast needs a `RectTransform`/`CanvasRenderer`/`TextMeshProUGUI` hierarchy under the Canvas — enough serialized surface area (font asset reference, material, extra settings) that hand-typing it blind risks a subtly broken result with no Editor validation to catch it. Left as a manual step: duplicate the existing `TooltipSkillPanel` (or the item tooltip's panel) in the Hierarchy, strip it down to a single text field, add the `PlayerFeedbackUI` component to the duplicated root, and wire `root`/`messageText` to it.
- **Still not covered**: "a pursued item can be destroyed mid-chase" (another player grabs it first, a future time-based despawn) — there's no multiplayer or despawn system yet to actually trigger this case.

## UI Window System

- **Window position is now saved to disk.** `WindowPanel` implements `ISaveParticipant` directly (see the save system section below), persisting each window's id, open/closed state, minimized state, and position (custom-dragged or cascade). Restoring re-opens a window exactly as it was left, including re-collapsing it if it was minimized.
- **`WindowLayoutManager` and every window assume a top-left anchor and pivot.** This is an implicit contract, not enforced by code — configuring a new window panel with a different anchor/pivot will silently place it in the wrong spot, with no error.
- **The cascade reads each window's width/height at layout time.** Fine for fixed-size panels; if a future window uses a `Content Size Fitter` or otherwise resizes based on content, its size at `Relayout()` time might not match its final size, causing subtle overlap.
- **Bring-to-front only fires on clicks that hit the window's background or its title bar (drag start).** Clicking directly on a child element (a button, a stat row) doesn't bring the window forward, since that element consumes the pointer event instead of bubbling it up.

## Lesson learned: destroyed Unity object references

- Comparing a cached `MonoBehaviour`/`GameObject` reference directly against `null` doesn't reliably detect "was destroyed while referenced" in the same way as a plain `bool` flag — Unity's overloaded `==` operator treats destroyed objects as equal to `null`, which caused a real bug in `WorldItemHoverDetector` (tooltip staying on screen after the hovered item was collected). Worth keeping in mind for any future system that caches a reference to something that can be destroyed at runtime (mobs, pickups, projectiles): prefer a separate `bool` flag alongside the reference rather than relying solely on the `== null` check.

## Lesson learned: Awake-ordering and GetComponent lookups

- **Caching a `GetComponent<T>()` result only in `Awake()` is fragile** if any *other* component might read that cached value before this component's own `Awake()` has run (Unity doesn't guarantee `Awake` order across different GameObjects). This caused a real `NullReferenceException` in `HealthBarUI` reading `HealthComponent.MaxHealth` before `HealthComponent`'s own `Awake()` had resolved its `CharacterStatsHolder`. Fixed by resolving lazily (on first access, cached from then on) instead of only in `Awake()` — safe regardless of who asks first. Worth using this pattern by default for any "look up a sibling component once" case, not just when a bug surfaces.
- **`GetComponent<T>()` only checks the exact GameObject hit, not its parents.** When a collider lives on a child object (e.g. an imported model's mesh, like Poring's `Geometry` child) but the component you actually need (`HealthComponent`, etc.) lives on the prefab root, `GetComponent` silently returns null instead of finding it. `PlayerTargetSelector` had this exact bug. `GetComponentInParent<T>()` is the safer default whenever a hit collider might not live on the same object as the data you need from it.

## Lesson learned: serialized scene references on dynamically-instantiated prefabs

- **A `[SerializeField]` reference to a scene object (e.g. the parent `Canvas`) cannot be pre-wired on a prefab asset that gets `Instantiate`d at runtime** — there's no scene instance to drag into the field at author time, so it silently stays `null` on every clone. This caused a `NullReferenceException` in `SkillBookEntryUI`'s drag-and-drop (needed its `Canvas` to parent a floating drag icon). Fixed by resolving it lazily via `GetComponentInParent<Canvas>()` in `Awake()` instead of a serialized field — the same pattern `ItemTooltipUI` already used for its own parent canvas. Worth defaulting to this pattern for any component that will be cloned from a prefab asset and needs a reference to whatever scene hierarchy it ends up parented under.

## Lesson learned: `.enabled` does not block Input System / UI-invoked calls

- **Setting a `MonoBehaviour.enabled = false` only stops Unity's own automatic lifecycle calls** (`Update`, `FixedUpdate`, physics messages, etc.) — it does **not** stop a public method on that component from being called directly. The new Input System's "Invoke Unity Events" bindings and Unity UI's `Button.onClick`/`IPointerClickHandler` both call the target method directly, bypassing `enabled` entirely. This caused a real bug: `PlayerDeathHandler.SetControlsEnabled(false)` disabled `CharacterMovementController`, `PlayerCombatController` and `PlayerInputRouter` on death, but WASD movement, click-to-move, and skill casting (via `SkillHotbarSlotUI`/`SkillInputRouter`, which was never in the disabled list at all) kept working anyway, because both routes call methods on those components directly rather than relying on `Update()`.
- **A `NavMeshAgent` keeps moving toward its last destination on its own**, independent of whatever script called `SetDestination()` on it. Disabling the calling script does not stop the agent — only `NavMeshAgent.ResetPath()` (or disabling the `NavMeshAgent` component itself) does. This meant a player already walking toward a clicked point at the moment of death kept sliding to that point even after "movement" was disabled.
- **The actual fix has two parts, applied together:**
  1. Every public method that can be reached from an Input System event or a UI click now self-guards instead of relying solely on the caller's `enabled` state: `CharacterMovementController.SetDirectionalAxis`/`SetClickDestination` check `!enabled` and return early; `PlayerSkillCaster.TryCastSkill` and `EquipmentManager.TryEquipFromInventory`/`Unequip` check a new `HealthComponent playerHealth` reference (`playerHealth.IsDead`) and return early/false. Basic-attack and healing needed no fix — `PlayerCombatController`'s attack loop already lived entirely in `Update()` (correctly stopped by `enabled = false`), and `HealthComponent.Heal` already self-guarded on `IsDead`.
  2. `PlayerDeathHandler.SetControlsEnabled(false)` now also calls `movementController.StopMovement()` (which calls `NavMeshAgent.ResetPath()`), so a pending click-to-move destination is actively cleared rather than just no longer being re-issued.
  - **General rule going forward**: disabling a component only protects code paths that run through Unity's own lifecycle calls. Any method reachable from a UnityEvent binding (Input System actions, `Button.onClick`, pointer handlers) needs its own internal guard if it must be blocked under some game state (death, stun, a cutscene, etc.) — `enabled` alone is not enough.
- **`Project.Items` now references `Project.Combat`** (added to `Project.Items.asmdef`) so `EquipmentManager` can hold a `HealthComponent` reference — checked for circular references first (`Project.Combat` only references `Project.Character.Stats`), no cycle.
- **Fixed: `PlayerLootController` now also self-guards on death.** It called `pendingPickup.TryCollect(inventory)` once in range with no death check, so a player who died while already within pickup range of an item could still collect it — the same class of bug as the rest of this section, just missed in the original pass since `PlayerLootController` was never in `PlayerDeathHandler.SetControlsEnabled`'s disabled list. Fixed with the same `HealthComponent playerHealth` reference pattern already used by `EquipmentManager`/`PlayerSkillCaster`: a new `[SerializeField] private HealthComponent playerHealth` field, checked at the top of `Update()` — if dead, the pending pickup is simply abandoned (`pendingPickup = null`) instead of being pursued or collected. **Needs one manual step**: the new field is optional (`playerHealth != null` guards it) but does nothing until wired — drag the Player's `HealthComponent` into `PlayerLootController`'s new `Player Health` slot in the Inspector.

## Class differentiation (implemented)

Basic-attack mechanics that vary by class or by equipped weapon, on top of the existing skill-based class restrictions:

- **Attack range now comes from the equipped weapon, not the class.** `ItemDefinition.AttackRange` is set per weapon (a dagger and a spear both being Melee doesn't mean they share a range); `PlayerCombatController.GetAttackRange()` reads it from whatever's in the main hand, falling back to `unarmedRange` when nothing's equipped. This applies to every class uniformly, including Mage — a Mage's basic attack range depends on whether their staff/wand is flagged `Ranged`, exactly like anyone else. Skill range is unaffected: it still comes from each `SkillDefinition.Range` independently (see `PlayerSkillCaster`).
- **`WeaponType` (Melee/Ranged)** on `ItemDefinition` drives the Archer's ammo mechanic below, decoupled from range itself — a weapon's range and its `WeaponType` are set independently, since they answer different questions ("how far" vs. "does ammo apply").
- **Archer ammo**: a dedicated `EquipmentSlot.Ammo` holds a stack count (`EquipmentManager.EquippedAmmoCount`), not a single worn item like the rest of equipment — equipping more of the same ammo type stacks onto what's equipped, equipping a different type swaps places directly with the source inventory slot (via a new `Inventory.SetSlot`, bypassing weight-capacity clamping intentionally, so a swap can never be partially blocked by weight). `PlayerCombatController.PerformAttack` consumes one unit per shot only while a `Ranged` weapon is in the main hand; wielding a `Melee` weapon (or being unarmed) never touches ammo at all, even if some is equipped. Out of ammo (or none equipped) while wielding a Ranged weapon falls back to a weaker (`archerBaseAmmoDamageMultiplier`, default 0.5×) but infinite base shot, floored at 1 damage (`Mathf.Max(1, ...)` — a naive multiplier could otherwise round down to 0 against low ATK, dealing silent zero damage with no error). Equipped ammo's `StatBonuses` only contribute to the character's stats while a Ranged weapon is equipped (`EquipmentManager.GetBonus`) — otherwise they'd passively boost melee stats too, which was an actual bug caught during this pass. Ammo count is shown via `AmmoCounterUI`, hidden entirely when no ammo is equipped (the base-shot fallback doesn't need a counter).
- **Dual-wielding (Thief)**: one-handed weapons can be flagged `ItemDefinition.CanBeOffHand`. Equipping a second one-handed weapon while the main hand already holds one auto-resolves to the off hand (`RightHand`) only if *both* weapons are flagged off-hand-capable; otherwise it replaces the main-hand weapon like a normal swap, and evicts an incompatible off-hand weapon if one was equipped (`EquipmentManager.ResolveTargetSlots`). `PlayerCombatController.IsDualWielding` distinguishes a genuine two-weapon setup from a two-handed weapon (which also occupies both hand slots) by comparing item references rather than just checking both slots are non-empty. Thief's basic attack lands a second hit at `OffHandDamageMultiplier` (0.5×) when dual-wielding.
- **Swordman block**: `PlayerBlockController` implements a new `IDamageModifier` interface, an optional hook `HealthComponent.TakeDamage` checks before applying damage. Gives Swordman a chance (`blockChance`, default 25%) to reduce or fully negate (`blockDamageReduction`, default 100%) an incoming hit. Deliberately decoupled — `HealthComponent` doesn't know blocking exists, `PlayerBlockController` is just one optional implementation of a generic "modify incoming damage" hook, so the same hook could later carry elemental resistance or other defensive mechanics without touching `HealthComponent` again.
- **Mage mana-cost basic attack**: consumes `mageManaCostPerAttack` (default 2) per basic attack, and can't attack at all below that cost (`PlayerCombatController.CanAttack`) — the only class where basic attack is resource-gated rather than always available.
- **Mage element selection exists but doesn't affect damage yet.** `PlayerElementController` tracks a `Water/Fire/Grass/Ground/Electric` selection with `SetElement`/`CycleElement`, but nothing reads `CurrentElement` when dealing damage — no input is wired to `CycleElement()` either. This becomes meaningful once an elemental resistance system exists (see "Planned skill system expansion" below, which already covers the general elemental-resistance shape needed).
- **`FireBolt` (Mage), `Mammonite` (Merchant), and `Envenom` (Thief) were finished** (previously unfinished stubs — see git history for the prior state of this note). All three now have a `skillName`/`description`, tuned `cooldownSeconds`/`range` distinct from the authoring-time defaults, and were confirmed added to `SkillBookWindowUI.allSkills` in `Prototype_Map01.unity` (they were not there before — the array only held BasicHeal/StrongHeal/Bash/Snipe). `Envenom`'s `targetType` (was `Self`) and `damageType` (was `Magical`) were corrected to `Enemy`/`Physical` — it previously would have resolved as a self-targeted magical effect instead of an enemy-targeted physical poison attack. **Remaining gap: none of the three have an `icon`.** The shared `SpellsIcon` sprite sheet (`Assets/Sprites/Classes/SpellsIcon.png`) only has 4 sub-sprites, already used by BasicHeal/StrongHeal/Bash/Snipe — there's no unused slice to assign, and adding new ones requires re-slicing the source image in Unity's Sprite Editor (art + an editor pass, not something to guess at from outside Unity). Until then these three will show a blank icon in the Skill Book and hotbar.
- **Aside, noticed while fixing the above, not touched**: `Bash.asset` has `damageMultiplierPerLevel: 100`, two orders of magnitude above every other damage skill (Snipe/FireBolt/Mammonite/Envenom all use `1`). Might be a deliberate design choice (Bash historically hits hard in Ragnarok Online) or might be a leftover typo from authoring — worth a deliberate look rather than assuming either way, since at level 5 this would multiply `StatusAtk` by 500.
- **No feedback (visual or audio) when a block lands** — a blocked hit currently looks identical to a normal hit that happened to roll low damage, from the player's perspective.

### Planned: real damage formula (documented ahead of time)

Basic-attack and skill damage currently apply a weapon/skill's contribution as a flat stat bonus feeding into `StatusAtk`/`StatusMatk` (via `EquipmentManager.GetBonus` → `CurrentSubStats`), with no separate consideration of the target. The intended replacement is a proper formula combining the player's base stats, the weapon's own stats, the target's weakness/resistance, and active buffs/debuffs — closer to how Ragnarok Online actually resolves a hit. Noted here ahead of time so the shape doesn't need to be re-derived later:

- **Entry point stays the same**: all offensive damage already funnels through `PlayerCombatController.DealHit(int baseDamage)` (normal attack, Thief's off-hand hit) and `PlayerSkillCaster.TryCastDamage` independently. The formula replaces how the `baseDamage`/`damage` value going into those is computed, not the surrounding attack flow.
- **Target weakness/resistance** is the natural next use of the `IDamageModifier` hook already built for the Swordman's block (see above) — an enemy-side implementation (e.g. `EnemyElementalWeakness`) could multiply incoming damage by element the same way blocking reduces it, without `HealthComponent` needing to change again.
- **Buffs/debuffs** feeding into the formula should fall out for free once the planned `IStatProvider` buff layer exists (see "Planned skill system expansion" below) — if the formula reads `CurrentSubStats`, active buffs are already included by the time it runs.
- **Weapon's own stats**: today a weapon only contributes via generic `StatBonuses` (STR/AGI/etc.), same as any other equipment. A real formula likely wants the weapon's own attack value as a distinct term rather than folding it into a stat bonus — worth deciding whether that's a new `ItemDefinition` field or derived from existing stat bonuses when this is tackled.

## Save / Persistence system (implemented)

**Correction, 2026-09-02**: an earlier revision of this section briefly claimed these files were missing from the repo, based on a stale local checkout of the connected folder that hadn't been re-synced before drawing that conclusion — the assumption was wrong, not the original implementation. `Project.Persistence`, `ItemDatabase`, `SkillDatabase`, and everything below are confirmed present and in active use (a live `NullReferenceException` from `PlayerSaveController.Save()` is what surfaced the bug fixed just below, which wouldn't be possible if the system didn't exist). Re-staging before concluding a file is missing is the actual lesson here — see the "Lesson learned" entries elsewhere in this document for the general pattern.

A `Project.Persistence` assembly implements a save/load system, addressing what had been the single largest known gap. It shipped in two passes — v1 covering player progression, v2 extending it to inventory, equipment, and UI state:

- **`ISaveParticipant`** is the extension point — any `MonoBehaviour` that owns persistable state implements `CaptureState(PlayerSaveData)`/`RestoreState(PlayerSaveData)`. `PlayerSaveController` discovers every implementation **in the loaded scene** automatically (via `FindObjectsByType<MonoBehaviour>(FindObjectsInactive.Include, FindObjectsSortMode.None)` filtered with `OfType<ISaveParticipant>()`), so adding a new persistable system needs no wiring in the save controller or the Inspector — only the interface implementation on the new component, wherever it lives in the hierarchy. This was widened from the original v1 design (`GetComponents<ISaveParticipant>()` on the Player GameObject only) specifically to reach `WindowPanel` instances, which live under the UI Canvas rather than the Player. `FindObjectsInactive.Include` matters here: a closed window is an inactive GameObject, and its layout still needs to be captured/restored.
- **`PlayerSaveData`** is a plain `[Serializable]` DTO holding only primitive-safe fields (`int`, `float`, `string`, `List<string>`, `List<int>`, `List<float>`) so it serializes cleanly with `JsonUtility` and keeps `Project.Persistence` a zero-dependency leaf assembly — no gameplay assembly reference runs from Persistence back into gameplay code, only the other way around. Cross-assembly references are stored as an id, an enum's underlying `int`, or a slot bitmask rather than a direct reference: a learned skill or inventory item is stored by a stable string id (see `SkillDatabase`/`ItemDatabase`), the Mage's element and the player's class are stored as their enum's `int` value, and an equipped item's occupied `EquipmentSlot`(s) — potentially more than one, e.g. a two-handed weapon — are packed into a single `int` bitmask (bit N set means slot N).
- **`ISaveRepository`** abstracts the storage mechanism behind `HasSaveData()`/`TryLoad()`/`Save()`; `JsonFileSaveRepository` is the only implementation today, writing a single JSON file to `Application.persistentDataPath`. This is the seam a future cloud save or server-side record (per the planned authoritative-server migration) would plug into without `PlayerSaveController` changing.
- **`PlayerSaveController`** loads automatically on `Start()` (configurable via a `loadOnStart` flag) and saves automatically on `OnApplicationQuit()`, so a prototype session isn't lost by default even though nothing else currently calls `Save()`. `Save()` and `Load()` are both public, ready to wire to a keybind, a menu button, or an autosave timer later.
- **`SkillDatabase`** (`Project.Skills`) and the new **`ItemDatabase`** (`Project.Items`) each resolve their respective ScriptableObject type to a stable string id (the asset's own name) and back, since `JsonUtility` can't serialize a direct ScriptableObject reference or a `Dictionary`. `PlayerSkillBook`/`PlayerSkillHotbar` hold a `SkillDatabase` reference; `PlayerInventory`/`EquipmentManager` hold an `ItemDatabase` reference (a new asset covering the project's 13 authored test items) — all four wired in `Prototype_Map01.unity`.
- **`Inventory` gained a public `EnsureSlotCount(int)`** method, growing by page (same 20-slot pages `TryAddItem` already allocates) until at least the requested count exists — needed because a restored save can specify more slots than a freshly-constructed inventory starts with. Restoring only calls the existing `SetSlot` for slots that were non-empty at save time; slots recorded as empty are left alone, since a freshly-added page already defaults to empty (and `SetSlot` isn't null-safe for its `item` argument, so this also avoids a `NullReferenceException` on a null item).
- **`WindowPanel` persists its own id, open/closed state, minimized state, and position** (whichever the window was actually using — a custom dragged position or the auto-cascade position) directly, with no new serialized reference needed. Restoring re-opens (or leaves closed) each window exactly as it was, then re-collapses it via the existing `ToggleMinimize()` if it was minimized — `Open()` itself always clears the minimized flag, so minimization has to be reapplied after.
- **What's covered now**: Base/Job level and experience, the six base stats and unspent stat/skill points, class, Zeny, every learned skill and its level, all 10 hotbar slot assignments, the Mage's selected element, full inventory contents (including previously-page-grown slots), every equipped item and the ammo count, and every window's open/minimized/position state.
- **Still out of scope**: nothing player-progression-related remains unsaved. Loot already collected from the world isn't captured. Enemy position, alive/dead status, respawn countdown, current HP, and whether it was actively engaging the player now persist across map switches (see the "Enemy world state" section below) but through a separate, in-memory-only mechanism (`EnemyWorldStateRegistry`), not through `ISaveParticipant`/`JsonFileSaveRepository` — so this state does not survive an app restart, only a map change within the same play session.
- **Scene wiring note**: `PlayerStatsController` gained two new methods (`SetValue`, `SetAvailablePoints` on the underlying `CharacterBaseStats`) purely to support restoring a saved value directly, bypassing the normal spend-a-point validation — the normal `TryIncreaseStat` flow is unaffected and still the only way stat points get spent during play.
- **Fixed: `NullReferenceException` in `WindowPanel.CaptureState` on quit**, when a window had stayed closed for the entire session. `rectTransform` was only ever assigned in `Awake()`, but a window's GameObject starts inactive when closed, and Unity does not call `Awake()` on a GameObject that is never activated — so a window nobody opened had a null `rectTransform` by the time `OnApplicationQuit` → `PlayerSaveController.Save()` → `CaptureState` tried to read its `anchoredPosition` (reached at all only because saving deliberately includes inactive objects, see above). Fixed the same way as the already-documented "Awake-ordering and GetComponent lookups" lesson below: `rectTransform` is now resolved lazily on first access (a `CachedRectTransform` property) instead of solely in `Awake()`, so it's always valid regardless of whether the window was ever opened.

## World / Map Navigation (implemented, v1)

A new `Project.World` assembly implements multi-map navigation: separate scenes connected by warp portals, matching Ragnarok Online's structure (each town/field is its own map, not one continuous world).

- **Two scenes now exist**: `Prototype_Map01` (original) and a new minimal `Prototype_Map02`, both registered in Build Settings. `WarpPortal_ToMap02` in Map01 leads to `SpawnPoint_FromMap01` in Map02; `WarpPortal_ToMap01` in Map02 leads back to `SpawnPoint_FromMap02` in Map01.
  - **Revision, 2026-09-02**: each `MapSpawnPoint` is now a child Transform of the `WarpPortal` it's conceptually paired with *in the same scene* — `SpawnPoint_FromMap02` (Map01) is a child of `WarpPortal_ToMap02` (also Map01), and `SpawnPoint_FromMap01` (Map02) is a child of `WarpPortal_ToMap01` (also Map02). This is the "arrival point for the portal that leads back to here" pairing, not "the portal you land next to" — a spawn point and the departure portal it's nested under are two different physical spots a few units apart (kept far enough apart to stay outside `activationDistance`, so arriving doesn't immediately retrigger a warp back). World positions were preserved exactly; only the hierarchy and local coordinates changed, so moving either object in the Editor now moves both together instead of them silently drifting apart.
- **The player and the camera-independent UI (canvas, event system) persist across scene loads via `DontDestroyOnLoad`**, rather than each map scene owning its own copy. `PersistentPlayerAnchor` (Player) and `PersistAcrossScenes` (UI Controller, EventSystem) both guard against duplicates: if the scene that originally held them is loaded again later (e.g. warping back), the freshly-spawned duplicate is destroyed immediately in `Awake()` instead of replacing the persisted original.
  - **Deliberate alternative not taken**: extracting the Player/Canvas/EventSystem hierarchy out of `Prototype_Map01.unity` into a separate always-loaded "Bootstrap" scene was considered and rejected — it would have meant hand-editing hundreds of interdependent Unity `fileID` references across a large YAML hierarchy with no Editor validation available, for no functional gain over the additive-component approach actually taken.
  - **Persistence and the static singleton reference are combined in one component (`PersistentPlayerAnchor`)** rather than split into two, specifically to avoid an `Awake()`-ordering race where a separate "registry" component could read a stale reference before the persistence component had run.
- **Camera and respawn point are re-wired per map at runtime, not serialized.** Unity can't serialize a cross-scene reference (the persisted Player and each map's local camera live in different scene files), so `MapBootstrap` — one instance per map scene — calls `IsometricCameraController.SetTarget()` and the new `PlayerDeathHandler.SetRespawnPoint()` once the map loads, pointing them at that map's own camera and respawn point.
- **Portal detection uses a per-frame distance check (`WarpPortal`), not a physics trigger.** Confirmed by inspecting the scene and project settings before choosing this: the Player GameObject has no Collider component, and the project has no Tags defined (`TagManager.asset` lists layers only) — a trigger-based design would have needed adding a collider to the Player, risking side effects on movement/combat systems that don't currently expect one. The same per-frame-check pattern is already used elsewhere in the project (see `WorldItemHoverDetector`/`EnemyController.DetectPlayer` above), so this stays consistent rather than introducing a second detection style.
- **Scene loading is synchronous (`MapTransitionService.WarpTo`, `SceneManager.LoadScene`)**, causing a brief hitch on transition. Acceptable for two small prototype maps; a loading screen / async load (`LoadSceneAsync`) is a natural follow-up once maps get larger or more numerous.
- **NavMesh must be baked manually per map in the Unity Editor.** Baked NavMesh data (`NavMeshSurface` + its generated `NavMeshData` asset) can't be authored outside the Editor — both maps' `NavMeshSurface` components now have baked data (`NavMesh-Ground.asset` in each map's scene-data folder), so a newly added map would need the same manual bake before it's walkable.
- **Each `WarpPortal` now has a visual marker**: a flat red disc (`WarpDisc`, a squashed built-in Cylinder mesh with a new opaque `WarpIndicator.mat`) sized to the portal's `activationDistance`, plus a floating world-space label (`WarpLabel`) reading "WARP" and the destination scene's name. `WarpLabel` is a true child Transform of its `WarpPortal` (not a scene-root object synced via script), so moving the portal in the Editor moves the label with it automatically through ordinary Unity parenting. It does not billboard to face the camera — same simplification the health bar labels use (their `viewCamera` field is also left unassigned), accepted here for consistency rather than introducing new rotation logic.
  - **Revision, 2026-09-02**: `WarpLabel` originally reused the `WorldSpaceHealthBarFollower` position-follow pattern from enemy health bars (a scene-root object whose `target`/`offset` fields pointed back at the portal). Re-parented to true hierarchy parenting instead, since the portal never moves at runtime — the follower's per-frame repositioning was pure overhead once `target` and the new parent were the same object, and true parenting is also what makes Editor drags of the portal move the label without needing Play Mode. The follower pattern remains correct for the enemy health bar case, where `target` is a different transform than the canvas's parent (see `Poring.prefab`) — this was a case-by-case call, not a reversal of that convention.

**Not yet implemented**: billboarding for `WarpLabel` (see above); a loading screen or fade transition during `MapTransitionService.WarpTo`; more than one player sharing the persisted-anchor pattern (irrelevant until multiplayer, but worth remembering the singleton is deliberately single-player-only); and any map beyond the two prototype scenes.

- **Fixed: `MissingReferenceException` on a destroyed `Camera` after switching maps, which blocked click-to-move entirely.** `PlayerInputRouter` and `WorldItemHoverDetector` both live on the persisted Player object (`PersistentPlayerAnchor`, `DontDestroyOnLoad`) but each held a direct Inspector reference to a `Camera` — the *previous* map's Main Camera, which is not persisted and gets destroyed on `SceneManager.LoadScene`. Unity throws `MissingReferenceException` (not a plain null reference) for exactly this: a serialized reference to a `UnityEngine.Object` that has since been destroyed. Fixed with the same re-wiring pattern `MapBootstrap` already used for the camera target and respawn point: both scripts gained a public `SetWorldCamera(Camera)` setter, `PersistentPlayerAnchor` gained accessors to reach them from outside, and `MapBootstrap` now pushes the new map's local `Camera` into both on `Start()`. General lesson: any persisted component that references a per-map object needs to go through this same runtime re-wiring — a plain Inspector reference across scene boundaries will always go stale the moment the old scene unloads.
- **Fixed: two more stale per-map camera references found while fixing the one above, both on the persisted Player.**
  - **`PlayerStatsCanvas` (the player's own floating HP/MP bar) spun to match the player's facing direction after a map switch instead of staying billboarded to the camera.** Its `WorldSpaceHealthBarFollower` had a `viewCamera` wired to the *previous* map's camera (unlike the enemy health bars, which deliberately leave `viewCamera` unset and never billboard at all — see the note on `WarpLabel` above). Once that reference went missing, the follower's `if (viewCamera != null)` check silently skipped billboarding every frame from then on — no exception, since a plain field read on a destroyed object doesn't throw the way a native call like `ScreenPointToRay` does — leaving the canvas to simply inherit the Player's rotation as an ordinary child Transform. Since `CharacterMovementController.Apply()` rotates the player root to face its movement direction (`transform.forward = intent.Direction`), the canvas rotated right along with it. Fixed the same way as the click/hover cameras: `WorldSpaceHealthBarFollower` gained a `SetViewCamera(Camera)` setter, `PersistentPlayerAnchor` gained a `StatsCanvasFollower` accessor, and `MapBootstrap` re-wires it on `Start()`.
  - **`CharacterMovementController.cameraYawSource`** (used to make WASD movement camera-relative) is resolved once in `Awake()` into a private `ICameraYawProvider cameraYawProvider` field and never revisited. This one would *not* have thrown after a map switch — `CurrentYaw` is a plain managed field read with no native Unity call in it, so it silently keeps returning the previous map's last yaw value forever instead of erroring — which made it easy to miss next to the two exceptions above. Fixed proactively by the same pattern before it surfaced as a bug report: a new `SetCameraYawSource(ICameraYawProvider)` setter, called from `MapBootstrap.Start()` with the new map's `localCamera` (already implements `ICameraYawProvider`, no new field needed).
- **Fixed: spawn position after warping silently kept the previous map's coordinates — confirmed root cause.** `MapTransitionService.WarpTo` searched for the destination `MapSpawnPoint` via `FindObjectsByType` immediately after `SceneManager.LoadScene` returned, on the assumption that the synchronous overload fully completes the new scene's object initialization before returning control to the caller. In practice the search found nothing on either map (`Debug.LogWarning` confirmed it in the Console — a diagnostic added specifically to settle this), meaning the destination scene's own objects were not yet queryable at that point despite the load call having returned — so the player was correctly left at their previous position, exactly matching the reported symptom. Fixed by no longer resolving the spawn point at the call site at all: `MapTransitionService.WarpTo` now only records the requested id (`PendingSpawnPointId`) and loads the scene; the actual search and `NavMeshAgent.Warp()` call moved into that map's own `MapBootstrap.Start()`, which Unity guarantees runs only once every object in the newly loaded scene (`MapSpawnPoint`s included) has already had its `Awake()` called. This sidesteps the exact synchronous-completion timing question entirely rather than depending on it. The `StopMovement()`-before-warping and "no match found" warning added alongside this moved with it into `MapBootstrap`.

## Enemy world state (implemented)

Two related bugs reported together, both stemming from enemies having no persistence at all: an enemy's `FaceDisplay` (a separate decorative mesh, not part of its main body renderer) stayed visible on screen after death instead of hiding with the rest of the enemy, and enemies reset to their scene-authored position every time the player left a map and came back — not the behavior expected of a persistent MMORPG world, where mobs should keep existing (and keep their respawn timers running) even off-screen.

- **`FaceDisplay` bug, root cause**: in both `Poring.prefab` and `Poporing.prefab`, the enemy's body is `EnemyGeometry` (the `MeshRenderer` wired into `EnemyDeathHandler.visualRenderer`), but the front-facing decal is a *separate* sibling-of-sorts GameObject, `FaceDisplay`, with its own independent `MeshRenderer` and `MeshCollider`. `EnemyDeathHandler.SetAlive(bool)` only ever toggled `visualRenderer` — it had no idea `FaceDisplay` existed as a second renderer, so it kept rendering (and kept its own collider live) through the entire death/respawn-wait window. Fixed by adding a `Renderer[] additionalRenderers` field to `EnemyDeathHandler`, toggled alongside `visualRenderer` in `SetAlive`, with each prefab's `FaceDisplay` renderer wired into it. Chosen as an array rather than a second single field so any future extra visual part (a second decal, an attached effect) can be added purely in the Inspector without another code change.
- **Position-reset bug, root cause**: `EnemyController.SpawnPosition` is captured fresh in `Awake()` from `transform.position` — i.e. wherever the enemy happens to sit in the scene file at the moment that scene loads. Map switches load the destination scene with `SceneManager.LoadScene(sceneName, LoadSceneMode.Single)` (see "World / Map Navigation" above), which fully destroys and reloads the *entire* previous scene, including every enemy. Since enemies have no `DontDestroyOnLoad` treatment (unlike the player, via `PersistentPlayerAnchor`) and no save-system participation (`ISaveParticipant` only covers player-owned state), each enemy is simply reconstructed from the scene file's authored transform on every load — any movement, death, or in-progress respawn countdown from before the map was left is silently discarded.
- **Fix: `EnemyWorldStateRegistry`** (new, `Project.World` assembly) — a static, in-memory dictionary keyed by `"{sceneName}:{enemyId}"`, holding an `EnemyWorldState` (position, alive/dead, and — if dead — the *absolute* `Time.time` the enemy should respawn at). `Project.AI` now references `Project.World` to use it (checked first for a cycle: `Project.World` references `Project.Character`, `Project.Character.Movement`, `Project.CameraSystem`, `Project.UI` — none of which reference back into `Project.AI`, so no cycle). Deliberately in-memory only, not written to disk through `ISaveRepository`: it only needs to survive scene reloads within the current play session, exactly the same scope `MapTransitionService.PendingSpawnPointId` already relies on for the same reason.
- **`EnemyDeathHandler` now saves and restores this state itself**, without any central orchestrator needing to know about it (same self-contained philosophy as `ISaveParticipant`, just scoped to one enemy instead of the whole player):
  - `OnDestroy()` — called by Unity on every enemy when `SceneManager.LoadScene` tears down the old scene, before the new one loads — saves current position, whether the enemy is alive, its current HP, whether it was actively engaging the player, and (if dead) the absolute respawn timestamp.
  - `Start()` — guaranteed to run only after every object's `Awake()` has already completed, including `EnemyController.Awake()` (which must set `SpawnPosition` from the scene-authored position *before* any restore logic moves the enemy, so the leash-range "home" point never drifts to wherever the enemy was last standing) — checks the registry and either warps the enemy to its saved position via `NavMeshAgent.Warp()` (direct `transform` assignment while the agent is active can fight the agent's internal state; `Warp` is the pattern this codebase already established for exactly this reason, see the `MapBootstrap`/`NavMeshAgent.Warp()` note in "World / Map Navigation" above), or — if it was dead — re-enters the existing hide/wait/respawn coroutine with whatever time remains until the saved respawn timestamp (already-elapsed time while the map was unloaded counts, since the stored value is an absolute timestamp rather than a countdown that would otherwise need to be paused/resumed).
  - `respawnDelaySeconds` handling was refactored into a shared `BeginRespawn(float delaySeconds)` helper so both a live death and a restored still-dead state go through the identical hide/wait/respawn path — only the delay differs.
- **Enemy identity**: `EnemyDeathHandler` gained a `[SerializeField] string enemyId`, defaulting to the GameObject's own name when left blank (`EffectiveEnemyId`). Both prototype maps currently have at most one `Poring` and one `Poporing`, so the name-based default is unique with zero required Inspector work; `enemyId` only needs to be set explicitly if a map ever gets two enemies sharing the same name.
- **Current HP and player-engagement now persist too**, closing what this section originally listed as a known limitation. `EnemyWorldState` gained `CurrentHealth` and `WasEngagingPlayer`. `OnDestroy()` now also captures `health.CurrentHealth` and whether `controller.PlayerTarget` was non-null at the moment the scene unloaded. On restore, an enemy found alive now also calls a new `ResumeEngagingPlayer()` — reacquiring the player via `PersistentPlayerAnchor.Instance` (the player object itself is never destroyed across scene loads, unlike enemies) and setting `controller.PlayerTarget`, then forcing `controller.ChangeState(new EnemyChaseState())` — before applying the saved HP. Forcing `EnemyChaseState` specifically (rather than trying to remember whether it was chasing or already attacking) is enough: `EnemyChaseState.Tick()` already re-evaluates distance every frame and transitions straight into `EnemyAttackState` on its own if the enemy turns out to already be in range, so only the coarser "was engaging" flag needs to be stored.
- **New `HealthComponent.SetCurrentHealth(int)`** restores a captured HP value directly (clamped to `[0, MaxHealth]`), deliberately not routed through `TakeDamage`/`Heal` — those carry combat side effects (`Died` firing at zero, the `IDamageModifier` hook) that a restore should not re-trigger. It's applied *after* the engagement restore above specifically so `HealthComponent.HealthChanged`'s own passive-mob retaliation check (in `EnemyController.HandleHealthChanged`) sees `PlayerTarget` already set and skips its own redundant `DetectPlayer()` call, instead of reacting to a HP restore as if it were a fresh hit landing.
- **Fixed an ordering hazard surfaced while wiring this in**: `EnemyController` and `EnemyDeathHandler` are two sibling components on the same GameObject, and while Unity guarantees every object's `Awake()` finishes before any `Start()` runs, it does **not** guarantee the order of `Start()` calls between two components on the same object. `EnemyController.Start()` used to unconditionally call `ChangeState(new EnemyIdleState())` — if Unity happened to run it *after* `EnemyDeathHandler.Start()` had already restored a chase state, it would silently overwrite the restoration back to Idle. Fixed by only defaulting to Idle `if (currentState == null)`, so the final state is correct regardless of which sibling's `Start()` runs first.

## Multiplayer / Persistence (out of scope for this phase, but relevant to the roadmap)

- **Everything runs fully client-trusted**, with no server validation — expected at this stage (pre-Fish-Networking/authoritative server), but the more systems that depend on this structure, the more expensive migration becomes later. Worth keeping in mind, for each new system, how it would eventually become a server-validated action. The new save system's `ISaveRepository` seam is deliberately positioned so this migration can swap the storage mechanism without touching every `ISaveParticipant`.
