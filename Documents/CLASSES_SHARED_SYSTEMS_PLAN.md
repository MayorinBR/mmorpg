# Other Five Classes — Shared Systems Plan

Source: [iRO Wiki — Mage](https://irowiki.org/wiki/Mage), [Merchant](https://irowiki.org/wiki/Merchant), [Acolyte](https://irowiki.org/wiki/Acolyte), [Thief](https://irowiki.org/wiki/Thief), [Archer](https://irowiki.org/wiki/Archer), consulted September 2026. Companion to `CLASSES_SWORDMAN.md` (same per-class-series intent, see its own header), but scoped differently: this is an architecture plan across all five remaining base classes, not a single class's implementation record. Purpose: find which skill mechanics repeat across classes so the shared system gets built once, not re-derived per class when each one's actual implementation pass happens. **Correction, 2026-09-14: this document originally claimed nothing in it was implemented yet, which was wrong — `CLASSES_SWORDMAN.md`'s own pass (dated two days earlier) had already shipped items 1 (status effects, stun-only), 2 (buff payload) and the HP regen-over-time system this document's item 1 also depends on, and this document's own text simply hadn't been reconciled against that when it was written.** See item 1 below for the corrected status, and the "Mage damage kit"/"Mage kit — extended", "Archer kit", "Acolyte kit" and "Thief kit" sections for the skills actually authored against this plan.

## Already covered by existing systems (data only, no new code)

Skills whose mechanic already has a home and just need authoring as an asset once that class is actually implemented:

- **Level-scaling single/multi-hit damage** (`SkillEffectType.Damage`, `CalculateDamage` = stat × multiplier × level): Fire Bolt, Cold Bolt, Lightning Bolt (Mage — "launch 1~level bolts, each MATK×1" is exactly this formula, multiplier 1; **now authored as assets, see "Mage damage kit" below**), Soul Strike, Holy Light (Acolyte — **now authored, see "Mage kit — extended again" / "Acolyte kit" below**), Double Strafe (Archer — **now authored, see "Archer kit" below**), Envenom's damage half (Thief — **now authored, see "Thief kit" below**), Stone Fling, Sand Attack (Thief — **now authored, see "Thief kit" below**). No new mechanic, just tuning + an `Element` value (see item 9 below, now resolved).
- **Mammonite** (Merchant) — a normal single-target Damage skill; **now fully authored, both halves** (`Mammonite.asset`, registered in `MerchantBase.asset` and the master `SkillDatabase.asset`) — the Zeny-cost half shipped 2026-09-18, see item 12 below.
- **Weapon-gated flat ATK passive** (`PlayerPassiveSkillController`, `SkillDefinition.PassiveRequiredWeaponSubtypes`) — no new instance of this among these five classes' passives (Thief/Archer passives below need a *different* generalization, not this one as-is — **that generalization shipped, see item 10**).
- **Mage's `PlayerElementController`** already exists (selectable attack element, currently "purely informational" per its own doc comment) — Fire Bolt/Cold Bolt/Lightning Bolt/Fire Ball/Fire Wall don't need it: each is its own skill asset with its own fixed `Element`, independent of the auto-attack element toggle. `PlayerElementController` stays relevant only for the Mage's basic (non-skill) attack.

## New shared systems needed (priority order — most skills unblocked per build first)

### 1. Status effects — IMPLEMENTED, widened beyond stun, 2026-09-17
`StatusEffectController` (`Project.Combat`) now holds six independent timed flags instead of a single stun timer: `IsStunned`/`ApplyStun` (unchanged), plus `IsPoisoned`/`ApplyPoison`, `IsSilenced`/`ApplySilence`, `IsBlinded`/`ApplyBlind`, `IsFrozen`/`ApplyFreeze`, `IsPetrified`/`ApplyPetrify`. Stun, Freeze and Petrify all fully immobilize in real RO, so they're additionally exposed as one `IsImmobilized` convenience property for every gate that doesn't care which of the three caused it. Each expire time is tracked independently (same "extend, don't shorten, a re-application that would end sooner" rule `ApplyStun` already had); re-applying Poison keeps the stronger of the two tick amounts while it's still active, or starts fresh at the new amount once the old one expired.

**Gates wired at the existing choke points**, matching the original plan's shape:
- **Movement** (`CharacterMovementController.Update`) and **basic attack** (`PlayerCombatController.CanAttack`) both now check `IsImmobilized` — a new optional `statusEffects` hook on each, same pattern as `buffs`/`defensiveStatsSource` elsewhere. **Correction**: this document previously claimed stun was "wired as an optional hook on both the player and `EnemyController`" — that was only ever true for the enemy side (`EnemyController.Update`, which already gated its whole AI tick + `NavMeshAgent` on `IsStunned`); nothing on the player actually checked it before this pass. Fixed as part of widening rather than left as a latent gap.
- **Skill cast** (`PlayerSkillCaster.TryCastSkill`/`TryCastSkillAtPosition`) gained the same optional `statusEffects` hook, checked via a new private `IsCastBlocked()` — blocked by `IsImmobilized` (Stun/Freeze/Petrify, same as any other action) or by `IsSilenced` alone (skill casts only; movement and basic attacks stay unaffected by Silence, matching real RO).
- **Poison's damage-over-time** ships inside `StatusEffectController` itself rather than reusing `PlayerHealthRegenController`'s primitive as originally sketched — regen and poison tick in opposite directions and don't share enough shape to be worth forcing into one component. A new optional `health` hook (`HealthComponent`) is ticked on its own `poisonTickIntervalSeconds` timer, calling `TakeDamage` with the tick amount recorded by `ApplyPoison`, `Element.Neutral`, `DamageCategory.Magical` — so it's mitigated by the target's magical defense like any other Magical hit, a documented simplification since real RO poison ignores defense entirely and this project has no "true damage" path yet.
- **Blind is the one exception**: the flag and `ApplyBlind` exist, but nothing reads `IsBlinded` yet (`ponytail:` comment on the property) — real RO's Blind sharply reduces Hit, but wiring that means touching every `HitChanceCalculator.RollHit` caller (player basic attack, skills, enemy attacks) for a status that Sand Attack now applies but nothing yet reads. Deferred until Blind's accuracy penalty is actually needed, same reasoning as Arrow Repel's knockback half used to be before item 11 shipped.

This unblocked, and as of 2026-09-18 all now ship: **Stone Curse** (petrify — see "Mage kit — extended" below; element-conversion-to-Earth still not modeled), **Frost Diver** (freeze — see "Mage kit — extended" below; element-conversion still not modeled), **Stone Fling**/**Sand Attack** (stun/blind chance — see "Thief kit" below), and **Envenom's poison half** (see "Thief kit" below, still plain `Physical`/`Neutral` damage until item 9 decides the Poison element — **resolved, see item 9 below; Envenom's damage now ships Poison-element too**). **Cure**/**Detoxify** (clear a status rather than inflict one) also shipped 2026-09-18 — see item 13 below for the new `StatusEffectController.ClearAllDebuffs()` method and `SkillEffectType.Cleanse` cast path, and the "Acolyte kit"/"Thief kit" sections for the two skills authored against it.

**Wiring audit, 2026-09-17**: before starting item 7, checked every `StatusEffectController` consumer in the codebase and the Player/enemy scene and prefab data for gaps. Every code-side gate (movement, basic attack, skill cast, the enemy AI tick) is wired consistently — confirmed by grepping every `IsStunned`/`IsImmobilized`/`IsSilenced`/etc. reference project-wide, no stale call sites left pointing at the old stun-only API. **Resolved, 2026-09-18: confirmed both the Player and enemies already have `StatusEffectController` wired in the Editor** (the component + its optional-hook fields on `PlayerCombatController`/`CharacterMovementController`/`PlayerSkillCaster`/`EnemyController`), so every gate documented above — and every status-inflicting skill authored since (Envenom, Stone Curse, Frost Diver, Sand Attack, Stone Fling) — is live at runtime, not just ahead of authoring.

### 2. Generalized buff/debuff payload — IMPLEMENTED
`BuffController` now carries a `BuffPayload` (`Assets/Scripts/Combat/BuffPayload.cs`): the original AtkPercent/DefPercent/MdefFlat trio, plus AspdPercent, MaxHealthFlat, and flat STR/AGI/VIT/INT/DEX/LUK. The old `ActiveBuff`/`PersistentModifier` structs and separate `Sum`/`SumPersistent` helpers collapsed into one `Total` property (`BuffPayload`'s own `+` operator sums the active list and the persistent dictionary); `ApplyBuff`/`SetPersistentModifier` now take a `BuffPayload` instead of a handful of loose floats/ints. `PlayerSkillCaster.TryCastBuff` builds the payload from three new `SkillDefinition` fields (`buffStatBonusPerLevel: StatModifiers`, `buffAspdPercentPerLevel`, `buffMaxHealthPerLevel`); `PlayerBerserkController` and `PlayerStatsController` were updated to the new signatures. `PlayerStatsController` folds a buff's STR/AGI/VIT/INT/DEX/LUK component into `effectiveStats` through a second, reused `JobBonusStatsView` layer (the same class already used for the Job Level bonus — no new decorator type needed), multiplies `CurrentSubStats`' Aspd by `BuffController.AspdMultiplier` the same way it already did for ATK, and adds `BuffController.MaxHealthBonus` in `GetMaxHealthBonus`.

One deviation from the original plan below: `BuffPayload` carries raw `int`/`float` fields rather than an actual `StatModifiers` value. `Project.Combat` cannot reference `Project.Items` (`StatModifiers`'s assembly) without creating a cycle — `Project.Items` already references `Project.Combat`. The conversion from `BuffPayload`'s raw fields to a real `StatModifiers` happens in `PlayerStatsController.ToStatModifiers`, which sits at the top of the assembly graph and can see both. `StatModifiers`'s constructor was made public and a `*(StatModifiers, int)` operator was added so `SkillDefinition.GetBuffStatBonus` can scale a per-level value the same way the other per-level getters do.

**Improve Concentration** (Archer) was the first buff skill authored against this infrastructure — see "Archer kit" below, including a documented gap: this payload has no percentage-stat channel, so real RO's +DEX/AGI% is shipped as a flat `buffStatBonusPerLevel` bonus instead. **Blessing, Increase AGI and Angelus** (Acolyte) now follow the same pattern — see "Acolyte kit" below.

**Bug found and fixed, 2026-09-17**: `SkillTargetType.Ally`'s own doc comment always claimed it "currently behaves the same as Self" until real ally selection exists, but `PlayerSkillCaster.TryCastBuff` never actually implemented that fallback — its ternary only special-cased `Self`, so an Ally-targeted buff fell into the Enemy-target branch instead (`targetSelector.CurrentTarget?.GetComponentInParent<BuffController>()`), which would silently fail (or worse, buff whatever enemy happened to be selected) instead of buffing the caster. Fixed by widening that condition to `TargetType == Self || TargetType == Ally`, making the code match the doc comment that was already there. This is what let Blessing/Increase AGI/Angelus below ship as real `Ally`-targeted assets instead of being mislabeled `Self`.

Original proposal (superseded by the above, kept for context): extend the buff payload to carry a flat `StatModifiers` delta (reusing the struct `ItemDefinition.StatBonuses`/`EquipmentManager.GetBonus` already use — same shape, no new type) alongside the existing Atk%/Def%/Mdef channels, plus add Aspd% and MaxHealth-flat channels since both recur here. Keep the existing timed-list + persistent-dictionary dual design (already proven by Provoke and Berserk) — nothing about *how* a buff expires or gets replaced needs to change, only *what* it can carry.

### 3. Party support (multi-target buff propagation)
No party/group system exists anywhere in this project today (confirmed — not mentioned in `FUTURE_IMPROVEMENTS.md` at all). Blocks real multi-target **Blessing**, **Increase AGI**, **Angelus** and Merchant's **Crazy Uproar** — the first three are now shipped as self-only casts instead (`Ally` target resolving to the caster, see item 2's bug note and "Acolyte kit" below), a deliberate stopgap the original text below already anticipated. This is still the biggest open prerequisite in this whole plan — Acolyte's real-RO identity is almost entirely party support, so whenever a real party model is built (even just "every other nearby player," since this project has no confirmed multiplayer grouping UI yet either), these three buffs are the ones to wire real propagation into first.

### 4. Stealth / detection (Hide–Reveal) — IMPLEMENTED, 2026-09-18, extended the same day
`StatusEffectController` gained an untimed `IsHidden` flag, `SetHidden(bool)`/`Reveal()`, deliberately not a timed expire-time field like every other status in item 1 — real RO's Hiding is a toggle, not a duration.

**Gated at the two places enemy AI acquires a target**, the same "choke point" approach item 1 used: `EnemyController.DetectPlayer()`'s fresh proximity scan now skips any hit whose player is hidden (a new `internal static bool IsPlayerHidden(Transform player)` helper — `GetComponentInParent<StatusEffectController>()` then `IsHidden`, null-safe so a player with no `StatusEffectController` wired is simply never considered hidden), and `EnemyWanderState.TryReaggroRememberedPlayer` (a Passive mob's memory-based re-engage of `RememberedAggressor`, which bypasses `DetectPlayer` entirely) checks the same helper before re-engaging. `EnemyChaseState` (an already-active chase) is deliberately untouched — see below.

**Hiding (Thief) toggles it**, see "Thief kit" below — the first real consumer, and the reason `SkillEffectType` gained a `Toggle` value. `EnemyChaseState` doesn't check `IsHidden`, so a mob already mid-chase when its target goes hidden keeps chasing instead of losing it — real RO's Hiding does break an active chase, but that needs a design decision (give up immediately, or keep moving toward the target's last known position?) that's better made once it's actually testable in-Editor (it now is, via Hiding) than guessed blind. **Resolved, 2026-09-18: the Boss/Insect/Demon exception (item 8, Race) is now built and wired** — `EnemyController.SeesThroughHiding` (true for a Boss-flagged enemy, or Insect/Demon race) is checked alongside `IsPlayerHidden` at both call sites above, so an enemy that should see through Hiding in real RO now does. **Editor wiring confirmed done, 2026-09-18** (see item 1's wiring audit) — Hiding is live at runtime.

**Reveal shipped as its own mechanic, 2026-09-18**: `SkillEffectType` gained a `Reveal` value and `PlayerSkillCaster` a new `TryCastReveal(skill, level)` — an `OverlapSphere` around the caster (reusing `SkillDefinition.AreaRadius` and `enemyLayer`, the same lookup `TryCastAreaDamage` already used) that calls `StatusEffectController.Reveal()` on every hidden target found, and — only for a target it just revealed — optionally also deals damage through the same hit-roll/size-scaling path as a Damage skill. Whether a Reveal skill also damages is decided purely by `CalculateDamage` returning non-zero, no separate flag: Sight's `damageMultiplierPerLevel` is 0 (reveal only), Ruwach's isn't (reveal and damage), matching how the two actually differ in real RO. This is `Reveal()`'s first caller. **Sight (Mage)** and **Ruwach (Acolyte)** are both authored against it — see "Mage kit — extended" and "Acolyte kit" below. `EnemyChaseState`'s reveal-during-chase gap (previous paragraph) is unaffected by this — Reveal only clears the hidden flag, it doesn't touch AI targeting directly.

### 5. Ground-targeted persistent zone skills — IMPLEMENTED, both halves, 2026-09-18
`SkillTargetType` gained a `Ground` value and `SkillEffectType` gained `Zone`. A Ground skill never has an "already selected" position the way an Enemy target can already be selected, so `PlayerSkillCaster.TryCastSkill` always routes it into `SkillTargetingController`'s picking flow (`BeginPicking`), same as a Damage skill with no valid target. `SkillTargetingController` was extended with a second picking mode alongside its existing enemy-picking one: when the pending skill is Ground-targeted, it raycasts the mouse against a new `groundLayer` every frame instead of `enemyLayer` (`HoveredGroundPointChanged` mirrors `HoveredEnemyChanged` for UI), and right-click calls the new `PlayerSkillCaster.TryCastSkillAtPosition(skill, position)` directly instead of going through `PlayerTargetSelector` — a ground point isn't a combat target.

`TryCastSkillAtPosition` mirrors `TryCastSkill`'s learned/cooldown/dead checks, then `TryCastZone` spends mana and spawns a new `SkillZoneController` (`Assets/Scripts/Combat/SkillZoneController.cs`) at the picked position via `SkillZoneController.Spawn(...)`. From there the skill decides which of two shapes the zone takes:

- **Damaging (Fire Wall)**: `zone.Initialize(...)` — ticks on its own interval (`SkillDefinition.ZoneTickIntervalSeconds`) for its duration (`GetZoneDuration(level)`), each tick rolling a fresh `Physics.OverlapSphere` against a target layer (reusing `PlayerSkillCaster`'s existing `enemyLayer` field — no new one needed) and applying a fixed damage/accuracy/element/category baked in at cast time, the same "resolve once at cast time" approach every other skill here already uses. Reused `SkillDefinition.AreaRadius` for the zone's radius and the existing Damage-header fields (`damageMultiplierPerLevel`, `damageType`, `element`, `accuracyBonusPerLevel`) for its per-tick damage, rather than adding parallel Zone-specific copies.
- **Attack-blocking (Safety Wall, Pneuma) — IMPLEMENTED, 2026-09-18**: `zone.InitializeBlock(AttackRangeKind)` instead of `Initialize(...)` — the "melee/ranged-block query" this section used to list as the still-open half. A new `Project.Combat.AttackRangeKind` enum (`Melee`, `Ranged`) is a deliberate mirror of `Project.Items.WeaponType` rather than a reuse of it, for the same assembly-cycle reason `BuffPayload` (item 2) and the zone-damage code above can't touch `Project.Items` directly. `SkillZoneController` gained a static `blockingZones` registry (`InitializeBlock` adds to it, a new `OnDestroy` removes from it) and a static `BlocksAttack(Vector3 position, AttackRangeKind rangeKind)` query — true if any registered blocking zone of that range kind covers the position. A blocking zone's own `Update` skips its damage-tick branch entirely (checked via a new nullable `blockedRangeKind` field) — it only exists to be queried, it never resolves its own hits. `EnemyAttackState.PerformAttack` calls `SkillZoneController.BlocksAttack(enemy.PlayerTarget.position, AttackRangeKind.Melee)` before its hit roll and returns early if blocked — hardcoded to `Melee` (`ponytail:` comment on the call site) since every enemy in this project attacks by standing next to its target (this is the only enemy attack state that exists); revisit if a ranged enemy attack is ever added. The symmetric player-attacks-a-blocked-target case (e.g. a monster standing inside its own Safety Wall) was deliberately not wired — no monster in this prototype casts these skills, so it has no observable effect yet, same YAGNI reasoning as everything else deferred in this document until it's actually needed.

New Zone-only `SkillDefinition` fields from the original (damage) half: `zonePrefab` (optional visual, null = logic-only), `zoneDurationSeconds`/`zoneDurationPerLevel`, `zoneTickIntervalSeconds`. New fields from this pass: `blocksAttacks` (bool) and `blockedWeaponType` (`Project.Items.WeaponType`, converted to `AttackRangeKind` at cast time in `PlayerSkillCaster.TryCastZone`).

Two deliberate scope decisions, one still standing and one now resolved:
- `SkillZoneController` lives in `Project.Combat`, so it does **not** apply `WeaponSizeModifiers` (that's `Project.Items`, downstream of `Project.Combat` — same assembly-cycle constraint as item 2's `BuffPayload`) — marked with a `ponytail:` comment. This matches real RO anyway: Fire Wall is spell damage, not a weapon hit. (Moot for a blocking zone, which deals no damage at all.)
- ~~This unblocks Fire Wall end to end but not Safety Wall/Pneuma~~ — **resolved, 2026-09-18**, see the attack-blocking bullet above. This unblocks **Fire Wall** (Mage — a pure "damage anything standing inside" zone, authored as `FireWall.asset`, see "Mage damage kit" below), **Safety Wall** (Mage, blocks melee, authored as `SafetyWall.asset`, see "Mage kit — extended" below) and **Pneuma** (Acolyte, blocks ranged, authored as `Pneuma.asset`, see "Acolyte kit" below) all the way through.

### 6. Instant AoE centered on a target/location (not the caster) — IMPLEMENTED, now also authored for Fire Ball, Thunderstorm and Arrow Shower
`SkillTargetType` gained an `AreaAroundTarget` value alongside the existing `AreaAroundCaster` (Magnum Break). `PlayerSkillCaster.TryCastDamage` still requires a valid target in range for `AreaAroundTarget` (same range/mana gate as a single-target skill, via `HasValidDamageTarget`), then bursts on it instead of hitting only it. The actual "hit everyone within `AreaRadius`" loop — previously `TryCastAreaDamage`'s own body — was extracted into a shared `ApplyAreaDamage(skill, level, center)`, called with `transform.position` for `AreaAroundCaster` and the resolved target's position for `AreaAroundTarget`; no duplicated hit-roll/damage code between the two. `SkillDefinition.IsAreaOfEffect` still gates whether a Damage skill is an AoE at all (kept as a separate bool rather than derived from `TargetType`, since nothing guarantees existing skill assets — e.g. Magnum Break's — already have `TargetType` set to match; safer to leave that bool as the single source of truth for now), while `TargetType` now decides *where* the AoE is centered and whether a target must be selected first.

This unblocked **Fire Ball**, **Thunderstorm** (Mage, see "Mage damage kit") and **Arrow Shower** (Archer, see "Archer kit"). `TargetType.AreaAroundCaster` combined with `SkillEffectType.Buff` (rather than Damage) was also reused, unmodified, by item 8's **Signum Crucis** — see "Acolyte kit" below.

### 7. Chance-based skill effects (success rate independent of Hit/Flee) — IMPLEMENTED, 2026-09-17
`SkillDefinition` gained a single `successChancePerLevel` field (`GetSuccessChance(level)`, exactly the plain-`Random.value`-roll shape the original text below proposed — no new RNG abstraction), reused by two different mechanics depending on `EffectType` rather than two separate fields:

- **Damage skills**: a new `InflictedStatus` field (`StatusEffectType`, see item 1) names a status the skill has a chance to inflict on a hit target, alongside three matching fields — `InflictedStatusDurationSeconds`/`PerLevel` and `PoisonDamagePerTickPerLevel` (only meaningful when `InflictedStatus` is Poison). `PlayerSkillCaster` gained `TryProcInflictedStatus`, called right next to the existing `TryProcStunAugment` at both Damage hit-resolution points (`TryCastDamage`'s single-target branch and `ApplyAreaDamage`'s loop) — rolls `GetSuccessChance(level)` and, on success, calls the target's `StatusEffectController.Apply(InflictedStatus, duration, poisonDamagePerTick)`, a new generic dispatcher on `StatusEffectController` itself that switches to the matching `ApplyStun`/`ApplyPoison`/etc. so callers never need their own switch. **A zero-damage Damage skill still procs this** — `TryCastDamage`/`ApplyAreaDamage` call `TryProcInflictedStatus` unconditionally once the accuracy roll lands, regardless of how much damage was actually dealt (`HealthComponent.TakeDamage` just no-ops on a non-positive amount) — which is what let **Stone Curse** ship as a pure "chance to petrify, zero damage" skill with no code changes (`damageMultiplierPerLevel: 0`), see "Mage kit — extended" below.
- **Enemy-targeted Buff skills (debuffs)**: `TryCastBuff` now rolls `GetSuccessChance(level)` before applying the buff, but only on the non-Self/Ally branch (a self/ally buff always lands, matching real RO) — a resisted debuff still spends mana and starts cooldown, the same "resource spent even on a miss" convention `TryCastDamage` already established for a dodged hit. `GetSuccessChance` defaults to zero for every skill authored before this field existed (Provoke, Endure, Blessing, etc.), and zero is treated as "unconditional, skip the roll" rather than "never succeeds" — so nothing already shipped changed behavior. **Extended, 2026-09-18**: the same resist roll is rolled independently per target by `PlayerSkillCaster.TryCastAreaDebuff` (item 8's Signum Crucis) — see that item and "Acolyte kit" below.

This unblocked, and as of 2026-09-18 all now ship: **Envenom**'s poison-inflict chance, **Frost Diver**'s freeze-inflict chance, **Stone Curse**'s petrify-inflict chance, **Stone Fling**/**Sand Attack**'s stun/blind-inflict chance, and **Signum Crucis**'s per-target resist roll — see "Thief kit", "Mage kit — extended" and "Acolyte kit" below. **Not covered**, deliberately: **Double Attack** (a proc chance on the player's own *basic* attack, not a skill cast — `PlayerCombatController`'s attack flow has no second-hit mechanic to gate yet, a different shape of problem than "does this skill's extra effect land") and **Steal** (RO's own steal-chance-vs-monster formula, plus needs loot/inventory access a skill cast doesn't have) — both stay class-exclusive future work, per the table below.

### 8. Monster classification: Race — IMPLEMENTED, 2026-09-18 (pairs with the already-tracked Size gap)
`CLASSES_SWORDMAN.md` item 5 already shipped monster **Size** (unblocking the weapon-vs-size damage table). This pass adds the matching **Race** axis, mirroring Size's own shape exactly: a new `MonsterRace` enum (`Assets/Scripts/Character/Stats/MonsterRace.cs`) — Formless/Undead/Brute/Plant/Insect/Fish/Demon/DemiHuman/Angel/Dragon, using real Ragnarok Online's own race IDs so the raw numbers match the wiki — plus a new `CharacterStatsDefinition.Race` field (`Formless` first, so every asset authored before this field existed defaults to the one race no bonus below keys off, same "safe default" reasoning `MonsterSize.Medium` used) and a companion `CharacterStatsDefinition.IsBoss` flag for the Hiding exception below. `IDamageable` gained a matching `Race` property (`HealthComponent.Race => StatsHolder.Stats.Race`), so any attacker or defender can read a target's/attacker's race the same generic way `Size` already works.

Four real skills and one existing mechanic were unblocked in the same pass, all authored/wired together since they're the same kind of addition:

- **Demon Bane / Divine Protection (Acolyte passives)** — `SkillDefinition` gained `passiveRaceDamageBonusPerLevel`/`passiveRaceDefenseBonusPerLevel`, and `PlayerPassiveSkillController` gained matching `GetRaceDamageBonus(MonsterRace)`/`GetRaceDefenseBonus(MonsterRace)` methods (summed across learned passives, zero unless the race argument is Demon or Undead — never weapon-gated, matching real RO). Unlike every other passive bonus in this project, these are **per-hit, not folded into `CurrentSubStats`**, since they depend on which specific target/attacker is involved: `PlayerStatsController.GetRaceDamageBonus`/`GetRaceDefenseBonus` expose them publicly, and `PlayerCombatController.DealHit` / `PlayerSkillCaster.TryCastDamage`/`ApplyAreaDamage` add the damage bonus in for a Physical hit against a Demon/Undead target. The defense side needed one more piece of plumbing: `IDefensiveStatsProvider` gained `GetRaceDefenseBonus(MonsterRace attackerRace)`, and `HealthComponent.TakeDamage` now resolves the attacker's race (`attacker.GetComponentInParent<IDamageable>()?.Race`) and adds the bonus into physical defense only (matching real RO's "soft DEF," which never mitigates magical damage) — this required `EnemyAttackState.PerformAttack` to start passing `attacker: enemy.transform` into `TakeDamage`, which it previously omitted entirely (harmless: nothing else reacts to the player's own `AttackedBy` event).
- **Decrease AGI (Acolyte debuff)** — pure data, no new mechanic: a normal Enemy-targeted `SkillEffectType.Buff` skill using `buffStatBonusPerLevel`'s existing AGI channel with a negative value, plus item 7's resist-chance field. Real RO's own Decrease AGI isn't race-restricted at all (unlike this document's own earlier — incorrect — note that it was), so it needed nothing from Race; grouped into this pass anyway since it's the same "Acolyte curse-type debuff" family as Signum Crucis below.
- **Signum Crucis (Acolyte AoE debuff)** — the first skill to combine `SkillTargetType.AreaAroundCaster` with `SkillEffectType.Buff` rather than Damage, so `PlayerSkillCaster.TryCastBuff` gained a dispatch to a new `TryCastAreaDebuff`: an `OverlapSphere` around the caster (reusing `enemyLayer`/`AreaRadius`, same as `TryCastReveal`) that rolls item 7's resist chance separately against every distinct, living Demon/Undead target found and applies a DEF-down `BuffPayload` (reusing the existing `DefPercent` channel Provoke already established) to each one that fails to resist. `ponytail:` comment flags the Demon/Undead race filter as hardcoded rather than a new per-skill race-filter field, since Signum Crucis is the only area debuff today. `TryCastBuff`'s own payload-building code was extracted into a shared `BuildBuffPayload` helper so it and `TryCastAreaDebuff` don't duplicate the same field-by-field construction.
- **Heal's Undead-damage interaction** — real RO's Heal inflicts damage (half the would-be heal amount) instead of healing when cast on an Undead-race target. `PlayerSkillCaster.TryCastHeal` gained a `GetUndeadTargetInRange` check: if the currently selected target is a living Undead in range, it's damaged instead of the caster being healed — reusing the already-selected `targetSelector` rather than routing Heal through the enemy-target-picking flow (`NeedsEnemyTarget` still deliberately excludes Heal, unchanged). **Ships as Holy-element damage as of 2026-09-18** (`Element.Holy`) — see item 9 below; previously shipped as Neutral while the element gap was still open.

### 11. Displacement / knockback — IMPLEMENTED, 2026-09-18
`Assets/Scripts/Combat/KnockbackUtility.cs` is the static helper this section originally sketched, built almost exactly as planned: `KnockbackUtility.Apply(NavMeshAgent agent, Vector3 sourcePosition, float distance)` computes the push direction away from `sourcePosition`, samples the nearest valid `NavMesh` point within `distance` via `NavMesh.SamplePosition`, and `agent.Warp(...)`s there — no coroutine, no physics, an instant reposition matching real RO's own knockback (falls back to pushing straight back along the agent's own facing if the source position is at, or extremely close to, the agent's own position). No-ops safely on a null agent or a non-positive distance.

`SkillDefinition` gained a single `knockbackDistance` field, reused by two different mechanics depending on `EffectType` — the same "one field, two consumers" shape item 7's `successChancePerLevel` already established:
- **Damage skills** (e.g. Arrow Repel): `PlayerSkillCaster.TryCastDamage`'s single-target hit branch calls `KnockbackUtility.Apply` on the hit target's own `NavMeshAgent` (`GetComponentInParent<NavMeshAgent>()`) right after `TryProcInflictedStatus`, only when `KnockbackDistance > 0`. Not wired into `ApplyAreaDamage` — no AoE skill in this project's roster needs knockback, so it stays a single-target-only mechanic until one does.
- **A new `SkillEffectType.Displacement`** (e.g. Back Slide): pushes the *caster* instead of a target. `PlayerSkillCaster` gained a `TryCastDisplacement` dispatched from `TryCastSkill`'s switch, plus an optional `NavMeshAgent agent` field for the caster's own agent (left empty, a Displacement skill can't be cast, the same "optional hook" convention every other optional dependency in this class already follows). Pushes away from the current target if one is selected, or straight back along the caster's own facing otherwise (`transform.position - transform.forward`, letting `KnockbackUtility`'s own near-zero-direction fallback handle the rest identically).

**Arrow Repel** (Archer) — `ArrowRepel.asset` updated in place with `knockbackDistance: 2` and its description text now mentions the knockback; no `SkillDefinition.cs` shape change was needed beyond the new field, since it was already a plain single-target Damage skill. **Back Slide** (Thief) — a new `BackSlide.asset`, `SkillEffectType.Displacement`, `TargetType.Self`, `maxLevel: 1`, `knockbackDistance: 5`. Both registered in their class's `*Base.asset` and the master `SkillDatabase.asset`. **Not modeled**: real RO's knockback can be blocked by standing against a wall/obstacle at the destination — `NavMesh.SamplePosition`'s own radius search already degrades gracefully (it clamps to the nearest valid point within `distance` rather than failing outright), so this project's version just always finds *some* valid landing spot instead of failing the knockback near an obstacle, a simpler and arguably more prototype-friendly behavior than real RO's own edge case.

### 15. Merchant carry-weight bonus — IMPLEMENTED, 2026-09-18
`Inventory.MaxCarryWeight` (`Project.Items`) converted from a constructor-fixed value into `baseMaxCarryWeight + weightCapacityBonus`, with a new `RefreshWeightCapacityBonus(float bonus)` that replaces (doesn't stack) the bonus — same "recompute from scratch on every refresh" convention `RefreshDependentMaxValues` already uses elsewhere for derived stats, so a delevel or respec can't leave a stale bonus behind.

**Architecture note — the interface-provider pattern (`IMaxHealthBonusProvider`/`IMaxManaBonusProvider`) was considered and deliberately NOT reused here**, despite this document's own earlier text suggesting it as "the one easy piece." Tracing the actual assembly graph (`Project.Items.asmdef`, `Project.Character.Combat.asmdef`) before writing any code found that `Project.Character.Combat` already references `Project.Items` one-way — giving `PlayerInventory` (in `Project.Items`) a direct reference to `PlayerPassiveSkillController` (in `Project.Character.Combat`), the way a provider-hook pattern would need, would have required the opposite reference too and created a cycle. `PlayerStatsController` already sits in `Project.Character.Combat` with legitimate, same-or-referenced-assembly access to both `PlayerInventory` and `PlayerPassiveSkillController`, and already has an established "composition root pushes a refresh" call site (`RefreshDependentMaxValues()`, triggered on `SkillLeveledUp`) — so the bonus push was added there instead: a new `[SerializeField] PlayerInventory inventory` field, and `RefreshDependentMaxValues()` now also calls `inventory.Items.RefreshWeightCapacityBonus(passiveSkills.GetWeightLimitBonus())` (null-guarded on `inventory`, `inventory.Items` and `passiveSkills`). `RestoreState()` (save-load) now also calls `RefreshDependentMaxValues()` before firing `StatsChanged`, so a restored save's already-learned Enlarge Weight Limit applies correctly at load instead of only after the next level-up.

`PlayerPassiveSkillController.GetWeightLimitBonus()` sums `passiveWeightLimitBonusPerLevel` across learned passives, mirroring `GetRaceDamageBonus()`'s unweighted-sum shape (item 8) rather than the weapon-gated shape most other passive sums use — carry weight isn't weapon-dependent.

**Enlarge Weight Limit** (Merchant) — `EnlargeWeightLimit.asset`, `SkillEffectType.Passive`, `passiveWeightLimitBonusPerLevel: 1000` (reaching +5000 at this project's level-5 cap), registered in `MerchantBase.asset` and the master `SkillDatabase.asset`. **Wiring note**: `PlayerStatsController`'s new `inventory` field is a `[SerializeField]` — needs the Player prefab's/scene object's `PlayerInventory` reference assigned in the Inspector before this bonus takes effect at runtime, the same one-time wiring step every other optional hook in this document already needed.

### 16. Toggle-and-drain buffs (Energy Coat) — IMPLEMENTED, 2026-09-18
`SkillEffectType` gained `ToggleDrain`, generalizing the previously Hiding-only `Toggle` case the way its own `ponytail:` comment already flagged as the trigger condition ("generalize... only if a second toggle status shows up") — but as a sibling effect type rather than widening `Toggle` itself, since a toggle-drain skill needs an ongoing per-second cost `Toggle` never had, not just a different flag to flip. `BuffPayload` (item 2) gained a new `IncomingDamageReductionPercent` component (appended last, so every existing positional constructor call stays valid), and `BuffController` a matching `IncomingDamageMultiplier` property (`Mathf.Clamp01(1f - Total.IncomingDamageReductionPercent)`, clamped so a reduction over 100% can't invert into amplification). `HealthComponent.TakeDamage` applies it as a third mitigation step, after defense: `amount = Mathf.Max(1, Mathf.RoundToInt(amount * buffs.IncomingDamageMultiplier))` — re-clamped to the same "always at least 1 damage" floor the defense step already enforces, rather than letting a strong reduction zero a hit out entirely.

A new `PlayerEnergyCoatController` (`Project.Character.Combat`) drives the toggle itself, deliberately modeled on `PlayerBerserkController`'s persistent-modifier pattern rather than `StatusEffectController.IsHidden`'s plain boolean flag — Energy Coat needs an ongoing per-second cost that Hiding never did, and `BuffController.SetPersistentModifier` already exists for exactly "a condition-triggered effect that stays active until its owner clears it." The trigger here is a player toggle instead of Berserk's HP threshold, and the "condition" is a mana-drain timer instead of a health re-evaluation: `Toggle(skill, level)` either applies the payload and starts a 1-second drain timer, or clears the payload if already active; each tick calls `mana.TryConsumeMana(...)` and auto-deactivates the moment a tick can't be paid, so Energy Coat silently turns off once SP runs dry rather than draining into negative. Two new `SkillDefinition` fields carry the per-skill numbers: `toggleDrainIncomingDamageReductionPercentPerLevel` and the flat, non-per-level `toggleDrainManaPerSecond` (mirroring `manaCost`'s own flat-regardless-of-level convention) — grouped under their own "Toggle Drain" header rather than the existing "Buff" header, since `EffectType` is `ToggleDrain`, not `Buff`, and this project's own convention is one header per `EffectType`.

`PlayerSkillCaster` gained an optional `energyCoat` field and a `TryCastToggleDrain` dispatch: pays `ManaCost` on/off (mirroring `TryCastToggle`'s own Hiding convention exactly — see item 4/"Thief kit"), then flips `PlayerEnergyCoatController.Toggle`. **Energy Coat** (Mage) — `EnergyCoat.asset`, `maxLevel: 5`, `toggleDrainIncomingDamageReductionPercentPerLevel: 0.06` (reaching real Ragnarok Online's own -30% at this project's level-5 cap — an exact match, unlike most other ported skills here), `toggleDrainManaPerSecond: 3` (flat; real Energy Coat's drain scales with level and current SP in a way this project's flat-per-tick model doesn't represent, the same "invented flat simplification" already applied to Hiding's on/off cost). Registered in `MageBase.asset` and the master `SkillDatabase.asset`. **Wiring note**: `PlayerSkillCaster`'s new `energyCoat` field is a `[SerializeField]` — needs a `PlayerEnergyCoatController` component added to the Player and wired into both this field and `PlayerSkillCaster.ownBuffs`'s existing `BuffController` before Energy Coat has any effect at runtime.

### 17. Shared crafting (materials → result item) — IMPLEMENTED, 2026-09-18
Arrow Crafting (Archer) and Aqua Benedicta (Acolyte) are mechanically the same shape — consume N units of material items from the caster's own inventory, produce M units of a result item — so rather than building two one-off skill-specific systems, this pass built one shared system both skills author against, matching this whole document's own stated purpose (find the repeated shape, build it once).

A new `Project.Items.CraftingRecipe` (`ScriptableObject`, alongside a small `CraftingMaterial` struct: an `ItemDefinition` + a quantity) defines a recipe as data, the same "instances are authored as assets" convention `SkillDefinition`/`ItemDefinition` themselves already follow. `Inventory` (`Project.Items`) gained three new methods: `GetQuantity(item)` (sums a stackable item's count across every slot it might span), `TryRemoveItem(item, quantity)` (removes across slots/stacks, failing atomically via an upfront `GetQuantity` check rather than partially consuming), and `TryCraft(recipe)` (checks every material is held AND the result would fully fit under `MaxCarryWeight` — both checked *before* anything is removed, so a failed craft never partially consumes materials — then removes each material and adds the result). An empty `Materials` list is valid and deliberately supported (`TryCraft` null-guards the iteration): Aqua Benedicta's only real "cost" in real Ragnarok Online is being cast near water, not an ingredient, so its recipe carries zero materials.

`SkillDefinition` gained a `craftingRecipe` reference and a `requiresNearWater` bool under a new "Crafting" header, and `SkillEffectType` gained `Craft`. `PlayerSkillCaster` gained optional `inventory` (a `PlayerInventory`, the same field `PlayerStatsController` already has from item 15) and `waterLayer` fields, plus a `TryCastCraft` dispatch: pays `ManaCost`, then — if `RequiresNearWater`, only after an `Physics.CheckSphere` against `waterLayer` within a new `NearWaterRadius` constant (3m) passes — calls `inventory.Items.TryCraft(skill.CraftingRecipe)`. Mana is spent even on a failed craft (not enough materials, no water nearby, or the result wouldn't fit), matching every other skill here's "resource spent once the cast is committed" convention. `ponytail:` comment on the water check: no map in this prototype tags anything with a Water layer yet, so it's ready but unexercised — the same "ready the moment one exists" pattern already used for the Undead/Demon race bonuses (item 8) before any such enemy existed.

Both skills reuse existing item assets rather than inventing new placeholder ones where a fitting one was already sitting in the project, following the "already in this codebase? reuse it" reflex: **Arrow Crafting** (Archer) — a new `ArrowCraftingRecipe.asset` consumes 1× `TestItem.asset` (this project's existing generic Material-type placeholder, part of the same "Test"-prefixed placeholder-item convention `TestNecklace`/`TestArmor`/etc. already established) to produce 10× the existing `AmmoTest.asset` — which, despite its filename, is already authored with `itemName: Arrow` and already registered in `ItemDatabase.asset`, so it needed no changes at all. `ArrowCrafting.asset` itself: `maxLevel: 1` (real Ragnarok Online's own Arrow Crafting doesn't meaningfully scale with level either), `manaCost: 1` (a nonzero placeholder — `ManaComponent.TryConsumeMana` treats an amount of exactly zero as an invalid request and always fails, so a truly free-to-cast skill isn't representable without changing that method; 1 SP is close enough), `requiresNearWater: false`. **Aqua Benedicta** (Acolyte) — a new `AquaBenedictaRecipe.asset` with zero materials, producing 1× a new `HolyWater.asset` (`ItemType.Material`, chosen over `Consumable` specifically to skip `ItemDefinition.OnValidate`'s "consumable with no restore effect" warning, since Holy Water has no restore effect to give — this project has no anti-Undead or curse-removal consumable mechanic yet for it to trigger, flagged in its own description text). `AquaBenedicta.asset`: `maxLevel: 1`, `manaCost: 1` (same zero-cost caveat as Arrow Crafting), `requiresNearWater: true`.
